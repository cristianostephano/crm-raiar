# Pitfalls Research

**Domain:** v1.6 — Importação de Clientes Ativos e Prospecção Separadas (adding features to the existing CRM Raiar codebase)
**Researched:** 2026-08-24
**Confidence:** HIGH for all codebase-specific findings below — every claim is read directly from `supabase/migrations/`, `lib/importacao/`, `lib/funil/`, `lib/agenda/`, `components/clientes/`, `components/layout/AppSidebar.tsx`, and `tests/`, not from web synthesis. No external web research was needed or used — every pitfall here is a concrete collision with an existing, already-shipped convention in this repo.

This file deliberately skips generic import-wizard or generic RLS advice — everything below is scoped to what breaks specifically when the 5 target features of v1.6 meet **this** codebase's existing conventions.

## Critical Pitfalls

### Pitfall 1: "Importar Clientes Ativos" cannot reuse `mover_card_funil`'s guard — it must duplicate it, and the two copies will drift

**What goes wrong:**
Every existing bulk-write RPC in this project (`importar_clientes_lote`, `atualizar_frequencia_visita_lote`, `atualizar_cnpj_lote`) is a raw, set-based `INSERT`/`UPDATE` that **never calls `mover_card_funil`** — they are structurally separate code paths. `importar_clientes_lote` today relies on the table's column *defaults* (`etapa` defaults to `'aguardando_contato'`, `status_acompanhamento` defaults to `'em_andamento'`) and never sets either column explicitly, so it has never had to reproduce any of `mover_card_funil`'s guards. "Importar Clientes Ativos" breaks that invariant for the first time: it must explicitly `INSERT ... (etapa, status_acompanhamento, cnpj, razao_social, cep, rua, numero, cidade, estado, ...) VALUES (..., 'primeira_venda', 'ganho', ...)` for every row — i.e. it lands rows **already at "ganho"** via a raw `INSERT`, not via the RPC that currently owns every "ganho" guard (CNPJ-01, the frequência-obrigatória guard from migration `0013`, and whatever razão-social/endereço guard this milestone adds to `mover_card_funil`, per Pitfall 2).

If the new import RPC is written the "obvious" way (copy `importar_clientes_lote`'s shape, add the two new status/etapa columns), none of `mover_card_funil`'s guards run — not because someone forgot a check, but because the two functions are separate PL/pgSQL bodies with **no shared call path**. Every guard added to `mover_card_funil` in the future (this milestone's razão-social/endereço widening, and any future guard) must then be hand-copied into the import RPC too, or the import path becomes a silent backdoor that creates "ganho" clients the drag-and-drop/manual flow would have rejected.

**Why it happens:**
This is the same shape as a pitfall this project has already hit once: migration `0019`'s discovery that `importar_clientes_lote`'s `jsonb_to_recordset` silently dropped `cnpj`/`nome_fantasia` because a second piece of the pipeline (the import RPC) wasn't updated in lockstep with the first (`mover_card_funil`'s new columns). Here the risk is structurally worse: it's not a missing column, it's a missing **guard**, and there is no compiler or RLS error to catch it — a row simply lands at "ganho" with no CNPJ, no razão social, or no address, exactly the states the guards exist to prevent for the manual/drag flow.

**How to avoid:**
Decide explicitly, at Discuss/Plan time, which of these two shapes the new RPC takes — do not let it default to "copy `importar_clientes_lote`":
1. **Duplicate the guard checks verbatim** inside the new import RPC (same style as `atualizar_cnpj_lote` "mirrors `atualizar_frequencia_visita_lote` arquivo por arquivo" — an accepted pattern in this codebase when the two operations are structurally different enough that sharing code isn't practical), with an explicit code comment cross-referencing `mover_card_funil`'s guard so a future edit to one triggers someone to check the other (mirrors this project's own convention of naming the sibling function in the header comment, e.g. `atualizar_cnpj_lote`'s and `atualizar_frequencia_visita_lote`'s mutual references).
2. Or extract the guard logic into a small pure `plpgsql` helper function (e.g. `campos_completos_para_ganho(razao_social, cnpj, cep, rua, numero, cidade, estado)` returning boolean) that both `mover_card_funil` and the new import RPC call — this is the first time this project would need a shared validation helper between two write RPCs, so it's a bigger design decision than "just copy the pattern," and should be sized accordingly in planning.
3. Whichever is chosen, since bulk import explicitly does **not** require frequência (per the milestone's own scope: "só a frequência de visita fica de fora"), the import RPC must *not* copy the frequência-obrigatória guard — it is the one guard that's supposed to diverge. Write this divergence down explicitly in the migration's header comment (this project's established documentation habit for every guard-carrying migration) so it reads as an intentional decision, not a missed copy-paste.
4. Because the import RPC bypasses `mover_card_funil` entirely, it also bypasses the **first-visita seeding logic** (the `if p_novo_status = 'ganho' and v_row_count > 0` block). An imported "ativo" client with no frequência will correctly get no seeded visita — but once its frequência is later set (either individually or via a future bulk-frequência flow), nothing seeds its first visita either, because `atualizar_frequencia_visita_lote` explicitly "deliberadamente não agenda visita nenhuma" (migration `0017`'s own comment). Confirm this is the intended behavior for imported-ativo clients (the new Agenda section nagging for missing frequência presumably becomes the trigger to fill it in via the *individual* ficha, which already seeds a visita through a different path — verify which UI action imported-ativo clients are expected to go through to get their first visita scheduled).

**Warning signs:**
A test that inserts a client via the new import RPC with an empty CNPJ, empty razão social, or missing address and it succeeds silently — this is the exact behavior the manual/drag "ganho" guard exists to prevent, so its absence here needs to be either an explicit, tested, and documented policy exception or a bug.

**Phase to address:**
The backend/migration phase that creates the new "Importar Clientes Ativos" RPC — must ship together with (not before) Pitfall 2's widened guard, since the import RPC needs to know the exact final shape of the guard it's duplicating or delegating to.

### Pitfall 2: Widening the "ganho" guard from 1 field (CNPJ) to 4 (CNPJ + razão social + endereço) breaks the single-field "effective value" pattern the grandfathering guarantee depends on

**What goes wrong:**
`mover_card_funil`'s current CNPJ-02 grandfathering is implemented as exactly one coalesce expression over exactly one column pair:
```sql
v_cnpj_efetivo := coalesce(nullif(btrim(p_cnpj), ''), nullif(btrim(v_cnpj_gravado), ''));
...
if p_novo_status = 'ganho' and v_encontrado and v_status_atual is distinct from 'ganho' and v_cnpj_efetivo is null then
  raise exception ...
```
Widening this to also require razão social + endereço means this pattern must be repeated **per field** — but "endereço" isn't one column, it's five (`cep`, `rua`, `numero`, `cidade`, `estado`; `complemento` is intentionally optional even in `createClienteSchema`, the manual-cadastro schema). That means the guard needs up to 5 more `v_<campo>_efetivo := coalesce(nullif(btrim(p_<campo>), ''), nullif(btrim(<campo>_gravado), ''))` computations, 5 more `select ... into` targets, and a single combined `and (v_razao_social_efetivo is null or v_cep_efetivo is null or v_rua_efetivo is null or ...)` condition — a meaningfully larger and more error-prone guard than the one-field CNPJ version this codebase has shipped so far. Missing even one of the five address sub-checks (e.g. forgetting `estado`) makes the guard technically "widened" but silently incomplete, and — critically — **the existing `cnpj-ganho.test.ts` test suite will not catch this**, because every seeded "legado" fixture in that file (`baseClienteFields`) already includes a full address. A guard that checks 4-of-5 address fields correctly and silently skips the 5th will pass 100% of today's tests and still leak incomplete "ganho" rows.

A second, sharper risk: `mover_card_funil` currently receives `p_cnpj` as a parameter the caller (the "ganho" dialog) explicitly sends. Razão social and the 5 address fields, by contrast, **already exist on the row** (they're edited via `ClienteDetailSheet`, not re-typed at "ganho" time) — so the natural design is for the widened guard to check only the *already-gravado* value (no new `p_razaoSocial`/`p_cep`/etc. parameters), unlike CNPJ which the dialog lets you fill in on the spot. If the plan copies the CNPJ shape literally (adds `p_razao_social`, `p_cep`, `p_rua`, `p_numero`, `p_cidade`, `p_estado` as new RPC parameters "for consistency"), `mover_card_funil` grows from 7 to 13 parameters, and the "ganho" dialog (`GanhoFrequenciaDialog.tsx`) — currently a two-field modal (frequência + CNPJ) — would need to become a 7-field modal embedding a full address form, which directly fights this project's core value ("cadastro rápido, poucos campos obrigatórios... mínimo de fricção") and this codebase's own established UX precedent (`GanhoFrequenciaDialog` is deliberately small; the full address form lives in `ClienteDetailSheet`, a separate screen).

**Why it happens:**
CNPJ was the first (and so far only) field this project made a "required-at-transition, not required-at-state" guard for, so there is exactly one precedent to generalize from, and that precedent's shape (one parameter, one coalesce, one dialog field) doesn't scale cleanly to a 5-column compound field like "endereço" without deliberate redesign, not copy-paste.

**How to avoid:**
- Treat "endereço completo" as a single derived boolean, not 5 independent guards spread through the function body — e.g. one `v_endereco_completo boolean := (v_cep_gravado is not null and btrim(v_cep_gravado) <> '' and v_rua_gravado is not null and ... )` computed from a single `select` of the row, mirroring the shape (one `select ... into` already reads `status_acompanhamento, cnpj` — extend that same select to read `razao_social, cep, rua, numero, cidade, estado` in one round trip, not five).
- Decide and document explicitly whether the new required fields are filled **inline in the ganho dialog** (requires growing `GanhoFrequenciaDialog` and `mover_card_funil`'s parameter list) or **must already be on the row before "ganho" is attempted** (the guard blocks with an error message like "Preencha razão social e endereço na ficha do cliente antes de marcar como ganho," and the vendedor is redirected to `ClienteDetailSheet` to fill them in first, then retries). The second option keeps `GanhoFrequenciaDialog` small (consistent with existing UX) and avoids growing the RPC signature again — flag this explicitly as a product decision for Discuss-phase, not an implementation-time default.
- Add a NEW grandfathering test case that today's suite is missing: a "legado" cliente inserted directly at `status_acompanhamento = 'ganho'` **with a full address but no CNPJ** already exists (`cnpj-ganho.test.ts`'s "legado" test) — add a sibling case with **no razão social and no address at all** (blank strings/nulls on every widened field) to prove the widened guard's grandfathering, since the current fixtures cannot exercise this path.
- Reuse the exact same transition-only 3-condition shape (`p_novo_status = 'ganho' and v_status_atual is distinct from 'ganho' and <field is empty>`) — this is the literal mechanism the project's own migration `0018` comment calls "the mechanism that guarantees CNPJ-02"; changing it to check current *state* instead of *transition* would retroactively block every "ganho" client that predates this milestone, the exact regression `PROJECT.md`'s Out of Scope entry ("CNPJ obrigatório retroativamente... grandfathering deliberado") explicitly forbids repeating.

**Warning signs:**
A plan that adds `p_razao_social`/`p_cep`/etc. as new `mover_card_funil` parameters without first confirming whether `GanhoFrequenciaDialog` is meant to grow into a full address form — that UX decision should come first and drives whether new parameters are needed at all. A test suite that still only exercises "legado sem CNPJ" and not "legado sem razão social/endereço."

**Phase to address:**
Same phase as Pitfall 1 (the "ganho" guard-widening migration) — plan it together with the import RPC, since both need the final shape of "what counts as complete" to agree.

### Pitfall 3: "Dia fixo" next-visit math needs a brand-new single-authority function, and the existing `proxima_data_visita` shape (fixed offset, always-forward) does not generalize to "Nth weekday of month" for free

**What goes wrong:**
`proxima_data_visita(p_base date, p_frequencia frequencia_visita_enum)` (migration `0013`) is `immutable`, table-access-free, and computes `p_base + interval '7/14 days'` or `+ interval '1 month'` — a pure fixed-offset calculation that is *always* strictly after `p_base` by construction (adding a positive interval to a date can never produce an earlier date). "Next Nth weekday of month" (e.g. "1st Thursday") is a fundamentally different kind of date math: it has to *search forward* from a base date to the next date matching a weekday+ordinal rule, and naive implementations of that search are exactly where the three named risks in this milestone's own description bite:
1. **Non-existent ordinal**: "5th Monday" doesn't exist in most months (only ~4-5 months/year have a 5th Monday) — a function that computes `first_monday + 4*7 days` without checking it's still in the same month will silently roll into the *next* month's Monday, which may or may not be the intended fallback (roll forward vs. clamp to the last occurrence of that weekday in the month are both defensible choices, but the choice has never been made in this codebase and must be explicit, not accidental).
2. **Never-in-the-past guarantee**: because `proxima_data_visita` today is a pure forward offset, "the suggested date is never in the past" has always been true *by construction*, with zero explicit code to enforce it. A weekday-search function has no such free guarantee — if a vendedor completes a visita late (e.g. concludes on the 20th, but "1st Thursday of this month" already passed on the 2nd), a naive "find the Nth weekday of the *current* month" search returns a **past date**, unless the function explicitly checks and rolls to next month when the computed date is `<= p_base`. This is exactly the failure mode the milestone description calls out, and there is no existing test or pattern in this codebase that exercises it (every existing `proxima_data_visita` test only needs to prove "adds N days/1 month," never "handle a stale/late completion").
3. **Timezone convention must survive the redesign**: every one of `proxima_data_visita`'s 2 call sites (`mover_card_funil`'s visita-seeding, `agenda_do_vendedor()`'s `proxima_data_sugerida` column) explicitly bases the calculation on `(now() at time zone 'America/Sao_Paulo')::date`, never raw `now()`, with an inline comment warning "o banco roda em UTC e, depois das 21h no horário local, o dia já teria virado o seguinte." A new/extended weekday-search function must preserve this exact pattern for its own "today" input — it's easy to introduce a new PL/pgSQL function that takes `p_base date` (safe, matches the existing signature) but then get careless in a *caller* that was written fresh for this milestone and passes `now()::date` directly instead of the São-Paulo-converted date.

**Why it happens:**
This project has, to date, only ever needed "add a fixed interval to a date" — a case date-fns/Postgres both handle for free with correct end-of-month clamping (the `0013` comment even notes "o intervalo de 1 mês do Postgres já faz o clamp de fim de mês"). "Nth weekday of month" is qualitatively new date math with no free clamping from either date-fns or Postgres interval arithmetic — it has to be hand-written, and hand-written date search logic is exactly where the "5th Monday" and "past date" edge cases hide.

**How to avoid:**
- Keep the single-authority pattern this project already established (`proxima_data_visita` is documented as "ÚNICA autoridade dessa conta em todo o projeto"): either extend `proxima_data_visita` with new optional parameters (`p_dia_semana int default null, p_semana_do_mes int default null`) that only apply when a client has "dia fixo" configured, or add a sibling pure function (`proxima_data_visita_dia_fixo`) that `proxima_data_visita` delegates to — but do **not** let the new weekday math get inlined separately into `mover_card_funil` and `agenda_do_vendedor()` as two independent copies; that immediately reintroduces the exact class of drift Pitfall 1 warns about for guards.
- Write the "5th occurrence doesn't exist" fallback rule down as an explicit product decision before writing SQL (roll to the *next* month's 1st occurrence being the safer default, since it never returns a date earlier than a naive computation and matches "wait, we'll catch the next one" sales-team intuition — but this is the project owner's call, not an implementation default).
- Add an explicit guard clause: after computing the candidate date, if `candidate <= p_base`, advance to the next month's occurrence — write a unit/integration test that pins `p_base` to a date *after* the target weekday's occurrence in the current month (mirroring how `proxima_data_visita`'s own tests already pin a fixed base date per the "recebe a data-base por parâmetro justamente para poder ser testada com datas fixas" comment) to prove the past-date case is actually covered, not just the happy path.
- Every new/changed call site must keep using `(now() at time zone 'America/Sao_Paulo')::date` as the base — grep both call sites (`mover_card_funil`, `agenda_do_vendedor()`) after the change and confirm neither regressed to a bare `now()::date`.
- Decide explicitly whether "dia fixo" retroactively applies to clients who are already "ganho" with a frequência already set (pre-v1.6) — the milestone description only mentions a new Agenda section for clients "sem frequência definida," which reads as scoped to clients missing frequência entirely, not to backfilling every existing ganho client with a "dia fixo" it never had. This is the **third** instance of this exact grandfathering question in this project (CNPJ-02 in v1.4, VIS-04/frequência in v1.3, now dia-fixo in v1.6) — follow the same established pattern: new columns nullable, no retroactive requirement, existing clients without a dia-fixo keep using the plain offset-based suggestion (or get no suggestion) until someone edits their frequência through the new flow.

**Warning signs:**
A test fixture where "today" happens to fall before the target weekday's first occurrence of the month (the easy, accidentally-always-passing case) — if every test in the plan only exercises that shape, the past-date bug will ship undetected exactly like `bucketDoItem`'s fuso-horário bug did before it was caught.

**Phase to address:**
The backend/migration phase implementing "dia fixo" — should ship its own dedicated test file (mirroring `proxima_data_visita`'s implicit test coverage inside `cnpj-ganho.test.ts`-style integration tests) with explicit cases for: mid-month completion (before target weekday), late-month completion (after target weekday, must roll to next month), and a "5th occurrence doesn't exist" month.

### Pitfall 4: Two required-ness profiles over the SAME 16-field `SYSTEM_FIELDS` list collide with an existing, already-present second source of truth (`createImportRowSchema`) that this milestone's plan can easily miss

**What goes wrong:**
Required-ness for the import flow is **already** defined in two independently-maintained places that happen to agree today only by convention, not by a shared source:
1. `SYSTEM_FIELDS[].required` (`lib/importacao/types.ts`) — drives `requiredFieldsFaltando()`, which powers Step 2's column-mapping "Continuar" disabled state and inline warning. Today: `required: true` on exactly `razaoSocial` and `responsavel`.
2. `createImportRowSchema` (`lib/validations/importacao.ts`) — a hand-written Zod schema, **not derived from `SYSTEM_FIELDS` at all**, that drives `annotarLinha`'s actual per-row pass/fail decision. Today: `.min(1, ...)` on exactly `razaoSocial` and `responsavel`, `.optional()` on every other field — hardcoded to match `SYSTEM_FIELDS` by the developer remembering to keep them in sync, with an explicit comment noting they "diverged" from `createClienteSchema` (the manual-cadastro schema) as of the last quick task.

This milestone needs **two different required-ness profiles over an identical field set** (prospecção: only `nomeFantasia` + `responsavel`; ativo: everything except `frequência` — which isn't even in `SYSTEM_FIELDS` today). This is a materially different shape than the two precedents this codebase already has for "a second import flow" — `lib/importacao/typesCnpj.ts` and `lib/importacao/typesFrequencia.ts` — because those two fork the *whole types file* (their own `SystemField` union, their own smaller field list) because their field **sets** genuinely differ from the 16-field client vocabulary. If this milestone's plan follows that same "fork the whole file" precedent naively (a plausible default, since it's the only precedent in the codebase), it produces a *third* full copy of the 16-field union + labels + `EXAMPLE_VALUES` map, this time with the exact same field set as the original — meaning any future field addition to `clientes` (a 17th SYSTEM_FIELDS entry) now has to be manually mirrored into 2-3 forked copies to keep the ativo/prospecção/original flows consistent, and nothing in TypeScript enforces that mirroring.

Compounding this: `annotarLinha.ts` does **not** currently read `SYSTEM_FIELDS[].required` at all — it hardcodes exactly two field checks (`RAZAO_SOCIAL_REASON`, `RESPONSAVEL_REASON`) against `createImportRowSchema`'s parse result. A plan that only touches `SYSTEM_FIELDS` (the "obvious" place, since it's named "vocabulário canônico... Fonte única") to add a second required-ness profile will not actually change what `annotarLinha` rejects, because `annotarLinha` isn't wired to that list's `required` flag in the first place — this is the single most likely "looks done but isn't" trap in this whole milestone: the column-mapping screen (Step 2) correctly nags about the right required fields, but the row-validation step (Step 3, `annotarLinha`) silently still only enforces `razaoSocial`/`responsavel`, because that's a third, independently-hardcoded surface.

A fourth surface with the *opposite* problem: `razao_social text not null unique` is a hard **database constraint** (migration `0002`, untouched by the recent `0023` address-optionality migration, which deliberately left `razao_social` alone). The v1.6 milestone text states prospecção import should accept a **blank razão social** ("razão social e o resto ficam opcionais"). If the import RPC (or the row-annotation layer) is changed to allow this without addressing the DB constraint, every blank-razão-social row fails the `INSERT` with a NOT NULL violation — and if the constraint *is* relaxed to nullable, `importar_clientes_lote`'s existing `on conflict (razao_social) do nothing` dedup silently stops deduplicating any blank-razão-social row, because Postgres unique constraints never treat two `NULL`s as conflicting — every re-upload of the same incomplete-name prospect creates a new duplicate client row, with zero error and zero warning. The application-layer dedup (`lib/importacao/dedupe.ts`'s `findDuplicates`) has the identical blind spot already built in: `normalizeRazaoSocial('')` returns `''`, and the loop explicitly does `if (!key) continue` — every blank-razão-social row is silently exempted from duplicate detection today, a pre-existing latent bug that this milestone is the first to actually exercise.

**Why it happens:**
`SYSTEM_FIELDS.required` was designed and named as "the" single source of truth when there was only one required-ness profile to describe, and the codebase's only precedent for "a second flow with different fields" (CNPJ/frequência imports) sidesteps the multi-profile problem entirely because those flows have disjoint field sets, not a shared set with different required flags — so there is no existing pattern in this codebase for what this milestone actually needs.

**How to avoid:**
- Before writing code, explicitly decide and document razão social's DB nullability for the prospecção path: either (a) razão social stays `NOT NULL` in the DB and the "obrigatório" milestone language is read as "product decision that turns out to require an explicit placeholder value auto-derived from Nome Fantasia at insert time when razão social is blank" (keeps the DB invariant, avoids the dedup blind spot, but needs its own explicit design), or (b) razão social becomes nullable — in which case the `on conflict (razao_social) do nothing` clause in whatever RPC handles this flow must be paired with an explicit `where razao_social is not null` dedup path, or a fallback dedup key (e.g. `nome_fantasia` normalized, the same way `razao_social` is today) for rows with no razão social, and `findDuplicates` in `dedupe.ts` needs a parallel fallback-key branch, not just its current razão-social-only key. This is a Discuss-phase decision, not an implementation detail.
- Refactor required-ness into a single per-field metadata shape that both `requiredFieldsFaltando` (mapping UI) and `annotarLinha`/`createImportRowSchema` (row validation) consume, parameterized by an import "profile" (e.g. `"prospeccao" | "ativo"`), rather than forking the whole `SYSTEM_FIELDS` array — reuse `SystemFieldDefinition<K>`'s existing generic-over-`K` shape (already built for `typesFrequencia.ts` in Fase 17) but keep `K` identical to `SystemField` across profiles, varying only the `required` map. Concretely: one shared field-metadata array (labels, keys, multi-flags — unchanged) plus a small `REQUIRED_FIELDS_BY_PROFILE: Record<ImportProfile, SystemField[]>` lookup, so a future 17th field only needs to be added in one place regardless of how many required-ness profiles exist.
- Whatever the mapping-UI change is, mirror it into `createImportRowSchema` (or replace the hardcoded Zod schema with one built dynamically from the same required-fields-by-profile source) — write an explicit test asserting that `annotarLinha`'s actual accept/reject behavior for a prospecção row with blank razão social matches what the mapping-screen's "Continuar" button implies is allowed, since today those two surfaces can already silently disagree and nothing catches it.
- Add a dedup test for a batch containing two rows with the same Nome Fantasia and no razão social (prospecção profile) — prove they're either both flagged as duplicates by whatever fallback key is chosen, or explicitly accepted as separate clients by product decision; do not let this path fall through `dedupe.ts`'s existing `if (!key) continue` silently.

**Warning signs:**
A plan that only lists `lib/importacao/types.ts` as a file to change for "required fields." A dedup test suite that never includes a blank-razão-social row. `annotarLinha.test.ts` cases that pass without any change to `lib/validations/importacao.ts`.

**Phase to address:**
The import-vocabulary/validation phase, planned explicitly as "touch mapping UI + Zod schema + dedup + DB constraint together" — should precede or ship alongside the wizard-UI phase for "Importar Clientes Ativos," since the wizard component depends on this shared vocabulary being correct first.

### Pitfall 5: Removing "Importar CNPJ"/"Importar frequências" from the menu is covered by tests that assert exact label text, href, and DOM order — and a separate Playwright suite navigates directly to the routes being retired

**What goes wrong:**
`tests/importacao/AppSidebar.test.tsx` has explicit unit tests asserting: the "Importar frequências" link renders for a Supervisor with `href="/clientes/importar-frequencias"` and is hidden for a Vendedor; the same for "Importar CNPJ" → `/clientes/importar-cnpj`; and DOM-order tests proving "Importar frequências" renders after "Importar clientes," and "Importar CNPJ" renders after "Importar frequências" — three tests keyed specifically to these two items' continued presence and relative position. Separately, `tests/e2e/importar-frequencias-guard.spec.ts` (and its sibling `importar-guard.spec.ts` for the CNPJ/original import routes) is a real Playwright suite that **navigates directly to `/clientes/importar-frequencias` by URL** (not via the menu) and asserts a Supervisor sees the "Importar frequências de visita" heading, while a Vendedor is redirected to `/`. Removing the menu entries without a coordinated decision on the routes themselves leaves three possible outcomes, only one of which is likely intended:
1. **Menu link removed, route left in place** — the page becomes an unlinked, still-fully-functional URL. `AppSidebar.test.tsx`'s presence assertions must be updated to "hidden for everyone" (not just "hidden for vendedor"), but `importar-frequencias-guard.spec.ts` still passes unmodified since it navigates by URL directly — this technically "still works" but leaves a route with zero discovery path, silently orphaned, and easy to forget when reasoning about what surfaces still exist.
2. **Route deleted along with the link** — `importar-frequencias-guard.spec.ts`'s supervisor case (which asserts the wizard heading renders) starts failing with a 404/Next.js not-found page instead of the expected heading; this is a hard test break, not a subtle one, but only if the E2E suite is actually run as part of verifying this milestone (Playwright suites are easy to skip in a fast local iteration loop compared to Vitest).
3. **Route deleted, DOM-order test for a link that no longer exists** — `AppSidebar.test.tsx`'s two "renders X after Y in DOM order" tests reference `.indexOf("/clientes/importar-frequencias")` and `.indexOf("/clientes/importar-cnpj")`; if those hrefs are simply gone from the rendered links array, `.indexOf` returns `-1`, and `expect(-1).toBeGreaterThan(...)` produces a **passing** assertion by accident (`-1 > 0` is false, so the test would actually *fail* here, which is the safe outcome — but the failure message will read as generic "expected -1 to be greater than X" noise rather than a clear signal pointing at "this test needs to be deleted, not fixed"), unless these three tests are explicitly deleted (not left to fail) as part of this milestone's plan.

**Why it happens:**
The menu-visibility tests and the route-guard E2E tests were written as two independently valuable, non-overlapping layers of coverage (DOM presence vs. actual server-side redirect behavior) — exactly the kind of coverage this project's `CLAUDE.md`/testing conventions ask for. That thoroughness is precisely what makes "remove a menu item" a bigger change than it looks: it's not a UI tweak, it's retiring a feature surface with tests at two different layers.

**How to avoid:**
- Decide explicitly (Discuss-phase) whether the two old routes (`app/(app)/clientes/importar-cnpj/page.tsx`, `app/(app)/clientes/importar-frequencias/page.tsx`) are deleted outright or merely unlinked. Given the milestone's own stated reason ("redundantes com a nova importação de ativos"), full removal (route + guard + page + wizard component + its dedicated `confirmar*`/`annotarLinha*`/`types*`/`modelo*` files) is the more likely intended outcome — but say so explicitly in the plan, since "just hide the menu item" is the smaller, easier-to-accidentally-ship version.
- If routes are deleted: delete `tests/e2e/importar-frequencias-guard.spec.ts` and the CNPJ-route cases in `importar-guard.spec.ts` in the same change, not as a follow-up — an E2E suite hitting a 404 is a real regression signal that should not linger even briefly on a shared branch.
- Update (not just leave failing) `AppSidebar.test.tsx`'s three affected test blocks (presence/hidden for "Importar frequências," presence/hidden for "Importar CNPJ," both DOM-order tests) in the same commit as the sidebar change — treat "grep the test suite for the exact strings being removed from the UI" as a standard step before considering a menu-item removal done, since this project's own `tests/importacao/AppSidebar.test.tsx` header comment already documents this exact test-per-item pattern was deliberately built for the *previous* menu addition (CNPJ/frequências import), so the same file is the natural place symmetric removal tests belong.
- Check for any other direct reference to these two hrefs beyond the menu and the E2E specs — confirmed via a repo-wide search that `ClienteDetailSheet.tsx` and other client screens do **not** currently deep-link to `/clientes/importar-cnpj` or `/clientes/importar-frequencias` (no "regularize this client" banner pointing there today), so the blast radius is contained to `AppSidebar.tsx` + the two `page.tsx` route files + their wizard/action/lib files + the two test files named above — but re-verify this with a fresh grep at implementation time in case anything changed between this research and execution.

**Warning signs:**
`npm run test`/Vitest green while `npx playwright test` is skipped or not run as part of this milestone's verification — the E2E break is the one most likely to go unnoticed if only the faster unit-test suite is checked before considering the phase done.

**Phase to address:**
The menu/UX phase that removes the two entries — should explicitly list "delete or update every test file listed in this pitfall" as an acceptance criterion, not an afterthought, and should decide route deletion vs. unlinking before writing any code.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|--------------------|-----------------|------------------|
| Duplicating `mover_card_funil`'s "ganho" guard logic verbatim inside the new "Importar Clientes Ativos" RPC instead of extracting a shared helper (Pitfall 1) | Fast to ship, matches this project's existing `atualizar_cnpj_lote`/`atualizar_frequencia_visita_lote` "mirror the sibling function" precedent | Every future guard added to `mover_card_funil` must be remembered and re-applied to the import RPC by hand, with no compiler/RLS signal if forgotten | Acceptable only if the migration's header comment explicitly cross-references the sibling guard (this project's established habit) so a future editor of one is nudged to check the other — never acceptable silently |
| Leaving `razao_social not null unique` untouched and instead auto-deriving a placeholder razão social from Nome Fantasia when the prospecção sheet leaves it blank (Pitfall 4, option a) | Avoids touching a DB constraint that many other flows (dedup, kanban card titles) implicitly depend on being non-empty | A placeholder value ("Nome Fantasia (sem razão social)" or similar) now exists in a column meant to hold a real legal name, and needs its own "is this a real value" convention everywhere razão social is displayed/exported | Acceptable as an MVP-scoped shortcut only if explicitly labeled in the UI (e.g. an "Incompleto" badge already exists per `lib/clientes/completude.ts` and could be extended to flag this) — never acceptable if it silently looks like a real razão social in exports/reports |
| Skipping a shared `dia_semana`/`semana_do_mes` retroactive backfill for clients that already have a frequência set before v1.6 (Pitfall 3) | Consistent with this project's 2 prior grandfathering decisions (CNPJ-02, VIS-04) — zero migration risk, zero risk of guessing a business owner's intent for existing clients | Existing "ganho" clients continue getting offset-based (not dia-fixo) suggestions indefinitely unless someone edits their frequência through the new flow | Always acceptable — this is this project's established, explicitly-approved pattern, not a corner cut |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|-----------------|-------------------|
| Postgres unique constraint (`razao_social`) + `ON CONFLICT (razao_social) DO NOTHING` dedup | Assuming a nullable, non-unique-violating blank razão social will still be caught by `ON CONFLICT` — Postgres never considers two `NULL`s a conflict under a unique constraint, so blank-razão-social rows never trigger the dedup path at all | If razão social becomes nullable for the prospecção path, add an explicit `where razao_social is not null` on the existing conflict-based dedup and a **separate** fallback key (e.g. normalized `nome_fantasia`) for rows with no razão social, mirrored in `lib/importacao/dedupe.ts`'s `findDuplicates` |
| Supabase PostgREST RPC calls (`supabase.rpc(...)`) when `mover_card_funil`/the new import RPC gain more parameters | Assuming parameter *count* growth alone is safe — this project's own migrations `0013`→`0018` already establish that `create or replace function` with a *different* parameter count creates an ambiguous overload unless the old signature is `drop function if exists`-ed first, in the same transaction | Any new migration touching `mover_card_funil`'s signature must `drop function if exists mover_card_funil(<exact old signature>)` before `create function` with the new signature — same pattern already used 3 times (`0002`→`0013`→`0018`) |
| `agenda_do_vendedor()`'s `proxima_data_sugerida` column vs. a "dia fixo"-aware `proxima_data_visita` | Changing `proxima_data_visita`'s signature without re-checking every existing caller (`mover_card_funil`'s visita-seeding block, `agenda_do_vendedor()`'s SELECT) for the new optional parameters | Grep both call sites after any signature change and confirm both either pass the new dia-fixo parameters or explicitly rely on sane `default null` behavior for clients without a dia-fixo set |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|-----------------|
| A per-row `select` inside the new import RPC to re-check `mover_card_funil`-style guards for every inserted row (instead of the set-based `INSERT ... ON CONFLICT` shape every existing import RPC uses) | Import of a few hundred rows starts taking noticeably longer, risking the ~10s Vercel Hobby execution ceiling this project's own Key Decisions table already flags for `importar_clientes_lote`'s set-based design | Keep the guard logic expressible as `CHECK`-style boolean conditions evaluable inside the same set-based `INSERT ... SELECT ... WHERE <guard conditions>` shape (rows failing the guard simply don't get inserted, surfaced back to the caller the same way `on conflict do nothing` rows are today), not a per-row PL/pgSQL loop | Would start to matter once import batches approach the scale where `importar_clientes_lote`'s existing set-based design was specifically chosen to avoid a 10s timeout — same threshold, no new risk introduced if the same set-based shape is preserved |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| New import RPC for "Importar Clientes Ativos" omitting the `is_supervisor()` guard that every other bulk-import/bulk-update RPC in this project carries (`importar_clientes_lote`, `atualizar_frequencia_visita_lote`, `atualizar_cnpj_lote` all check it first) | A Vendedor could bulk-create "ganho" clients bypassing every guard the funnel normally enforces — directly contradicts `PROJECT.md`'s explicit, already-shipped decision that bulk import stays Supervisor-only | Copy the `if not is_supervisor() then raise exception ...` guard verbatim as the very first statement in the new RPC body, same as its three siblings |
| Trusting the client-submitted `dia_semana`/`semana_do_mes` values for "dia fixo" without server-side re-validation against the enum/range of valid values | A tampered request could set an out-of-range weekday/week-of-month value that later breaks the date-search function in an untested way (e.g. an invalid ordinal never matching, silently returning `null` forever) | Re-validate range/enum server-side inside the RPC itself (mirrors this project's existing pattern of re-validating `motivo_conclusao_remota_id` and resumo length inside the RPC, not just trusting the dialog's client-side constraint) |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|--------------|-------------------|
| A prospecção-imported client with blank razão social shows a blank/empty kanban card title and an empty page title in `ClienteDetailSheet` (razão social is the only identifier used in both today) | Vendedor can't tell which card is which in the funil, defeating the purpose of importing prospects at all | Fall back to displaying Nome Fantasia wherever razão social would render blank — audit every place `cliente.razao_social` is rendered directly (kanban card, ficha header, dashboard tables) before shipping blank-razão-social support |
| Widening the "ganho" guard to require razão social + endereço, but only surfacing the failure as a raw RPC error inside the small `GanhoFrequenciaDialog` | Vendedor sees a generic error, has no clear path to "go fill in the missing fields," and may abandon the flow entirely | If the dialog stays small (recommended in Pitfall 2), its error state should link directly to opening `ClienteDetailSheet` for that same cliente pre-scrolled/focused to the missing fields, not just show red text |
| New Agenda section for "clientes ativos sem frequência definida" competing for attention with the existing atrasado/hoje/próximos buckets | If poorly separated visually, a vendedor might not realize this is a *different kind* of pending action (data completeness, not a task/visita) | Keep it a visually distinct section (not merged into the 3 existing buckets), consistent with how this project has always treated "different kind of pending thing" as a separate section rather than overloading `bucketDoItem`'s existing three-way split |

## "Looks Done But Isn't" Checklist

- [ ] **New import RPC honors every "ganho" guard:** Insert a row via the new RPC with an empty CNPJ, empty razão social, or missing address field and confirm it's rejected — not just that the happy path with full data succeeds (Pitfall 1).
- [ ] **Grandfathering extends past CNPJ:** A "legado ganho" fixture with **no razão social and no address** (not just no CNPJ) can still be read/edited/reaffirmed as ganho without being blocked by the widened guard (Pitfall 2).
- [ ] **Dia-fixo suggestion never lands in the past:** Test a completion where "today" is already past the target weekday's occurrence in the current month, confirm the suggested date rolls to next month, not backward (Pitfall 3).
- [ ] **Row-validation (`annotarLinha`) actually matches the mapping-screen's stated required fields:** For the prospecção profile, upload a row with blank razão social and confirm it's accepted end-to-end (mapping screen AND row validation AND the actual DB write), not just accepted at the mapping-screen step (Pitfall 4).
- [ ] **Blank-razão-social dedup works:** Two prospecção rows with the same Nome Fantasia and no razão social are flagged as duplicates (or explicitly, deliberately treated as distinct — confirm which was decided), not silently both inserted (Pitfall 4).
- [ ] **Menu removal is complete on both test layers:** `AppSidebar.test.tsx`'s label/href/DOM-order tests for the two retired items are deleted or updated, AND the corresponding Playwright E2E specs are deleted or updated — run both suites, not just Vitest (Pitfall 5).

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|-----------------|------------------|
| New import RPC missing a guard `mover_card_funil` has (Pitfall 1) | MEDIUM | New migration (never edit a pushed one) adding the missing guard condition to the import RPC via `create or replace function`; audit already-imported rows for violations (e.g. `select * from clientes where status_acompanhamento = 'ganho' and (cnpj is null or razao_social = '')`) and decide case-by-case whether to grandfather them in or ask the Supervisor to regularize via the ficha |
| Widened guard incorrectly checks state instead of transition, retroactively blocking pre-v1.6 "ganho" clients (Pitfall 2) | MEDIUM–HIGH | Same recovery shape as this project would have needed for a CNPJ-guard regression: new migration reverting the guard to the transition-only condition; audit whether any legitimate `mover_card_funil` calls were rejected in the interim (check for RPC error logs / support reports) |
| "Dia fixo" suggestion computed a past date once shipped (Pitfall 3) | LOW | New migration fixing the roll-forward logic in the shared date function; no data corruption risk since the RPC's actual write always requires vendedor confirmation (`concluir_visita`'s `p_proxima_data` is supplied by the caller, never auto-applied) — only the *suggestion* was wrong, not any committed data |
| `annotarLinha` and the mapping-screen required-fields disagree (Pitfall 4) | LOW–MEDIUM | Since this is a pure-function bug (no schema change), a follow-up commit correcting `createImportRowSchema` (or its dynamic-profile replacement) is a same-day fix; no migration needed unless the DB constraint itself (`razao_social not null`) also needs revisiting |
| Menu/route removal broke the E2E suite (Pitfall 5) | LOW | Delete or update the affected spec file(s) in a follow-up commit; no runtime/user impact since this is test-only breakage |
