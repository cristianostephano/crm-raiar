# Phase 4 — UI Design Contract

> Visual and interaction contract for the Dashboard Gerencial: a read-only screen showing clientes por etapa (bar chart), ganhos x perdidos + taxa de conversão (big-number stat tiles), desempenho por vendedor (horizontal bars, Supervisor-only), and prospecção por produto/categoria (horizontal bars), behind a top-of-screen period filter. This phase INHERITS the design-system foundation locked in `01-UI-SPEC.md` and extended in `02-UI-SPEC.md`/`03-UI-SPEC.md` — shadcn `nova` preset, blue-only accent, 8-point spacing, and the existing status colors (green=ganho, red=perdido, amber=atrasado). This is the **first data-visualization phase** in the project, so it also establishes chart-specific conventions (bar fill color, chart empty/loading states, number formatting, hero-number sizing) that did not exist before — these are documented explicitly as extensions, not silent departures. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Spacing Scale

Inherited unchanged from Phases 1-3 (multiples of 4): `xs 4px / sm 8px / md 16px / lg 24px / xl 32px / 2xl 48px / 3xl 64px`.

Exceptions added this phase:

| Exception | Value | Reason |
|-----------|-------|--------|
| Chart container height (fixed-count charts: etapa) | `280px` fixed | Recharts' `ResponsiveContainer` renders at zero height without an explicit parent height (a known pitfall) — always pair `ChartContainer` with `className="h-[280px] w-full"` |
| Chart container height (variable-row-count horizontal bars: vendedor/produto/categoria) | `min 280px`, grows `40px` per row, `max-height 480px` then internal vertical scroll | These lists grow as Supervisors add produtos/categorias (Phase 3) or hire vendedores — a chart that grows unbounded would push the rest of the dashboard off-screen; capping + scrolling keeps the page layout stable regardless of list size |
| KPI stat card padding | `lg` (24px), not `md` | The stat number is the loudest thing on the card (dataviz "hero figure" convention) — generous padding gives it room to read as a distinct, important number rather than a cramped label+value pair |
| Gap between the 3 KPI cards | `md` (16px) in a 3-column grid (desktop), stacked full-width (mobile) | Matches the grid-gap convention already used for the kanban board's column gaps in Phase 2 |
| Gap between chart Cards (etapa / vendedor / produto+categoria blocks) | `lg` (24px) | Larger separation between distinct chart blocks than between elements within one chart — keeps each metric visually independent, per the dataviz principle that "the data is the only thing allowed to be loud" (excess block-to-block proximity competes for attention) |
| Period filter row | sits directly below the page title/subtitle, `md` (16px) gap above the first chart block | Matches the "toolbar directly below heading" pattern already established for the Clientes screen's search/filter row (Phase 2) |

## Typography

Inherited from Phase 1-3's 4-size/2-weight scale (14/16/20/28, weights 400/600) with **one deliberate, documented exception this phase**:

| Role | Size | Weight | Line Height | Notes |
|------|------|--------|-------------|-------|
| Body | 16px | 400 | 1.5 | Chart axis tick labels, tooltip content, form-adjacent copy |
| Label | 14px | 600 | 1.5 | KPI stat-card labels ("Ganhos", "Perdidos", "Taxa de conversão"), chart card titles' small caption line |
| Heading | 20px | 600 | 1.2 | Chart Card titles ("Clientes por etapa do funil", "Desempenho por vendedor", "Prospecção por produto", "Prospecção por categoria") |
| Display | 28px | 600 | 1.2 | Page-level title "Dashboard" |
| **Stat (new — phase-4 exception)** | **36px** | **600** (reuses the existing semibold, no 3rd weight added) | **1.1** | **Reserved exclusively for the 3 KPI hero numbers** (Ganhos count, Perdidos count, Taxa de conversão %). Justification for extending the locked 4-size rule: D-05 is an explicit functional requirement that these numbers read as "grandes, diretos" — this is the project's first data-viz screen, and reusing Display (28px, already used once per page for the "Dashboard" title) would make the KPI numbers the same size as the page heading, undershooting a hero-figure's job of being the single loudest element on its own card. This is the ONLY new size in the project; do not reuse it anywhere else, and do not introduce a 6th size later without the same explicit justification standard |
| Meta/help text (precedented in Phase 2) | 14px | 400 | 1.4 | Chart captions (e.g. "Situação atual — não é afetado pelo filtro de período"), empty/error/loading copy inside chart cards |

**Number formatting:** all counts and percentages use `pt-BR` locale (`Intl.NumberFormat("pt-BR")`) — thousands separated by `.`, decimals by `,` — matching every other Portuguese-language surface in this project. KPI counts (Ganhos/Perdidos) render as plain integers, no compact K/M notation (data volumes are hundreds, not thousands, at this project's stated free-tier scale — compact notation would be premature abstraction). Taxa de conversão renders with exactly 1 decimal (e.g. `"42,3%"`) — small counts make 0-decimal percentages jump in large, confusing steps. Stat-tile numbers use the font's default proportional figures (not `tabular-nums` — that's reserved for table/axis columns where digits must align vertically, not a single standalone hero number).

## Color

Inherited base roles unchanged from Phases 1-3 (`--background`, `--card`/`--secondary`, `--primary` blue, `--destructive` red, `--success`/`--warning` from Phase 2). No new hex values are introduced this phase — only new *usages* of existing tokens.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (white / `oklch(0.145 0 0)` dark) | Page background behind the dashboard content |
| Secondary (30%) | `--secondary` (light gray `oklch(0.97 0 0)`) / `--card` (white) | KPI stat cards, chart Card containers, period-filter Select/Popover surfaces |
| Accent (10%) | `--primary` blue (`oklch(0.546 0.215 262.881)` light / `oklch(0.623 0.188 259.815)` dark) | Reserved for: the "Aplicar período" button inside the custom-range Popover, focus rings, **and — new this phase — every chart bar fill** (etapa/produto/categoria/vendedor bars all use this same blue, mapped onto shadcn's `--chart-1` CSS variable). **Implementation note:** `app/globals.css` already scaffolds `--chart-1` through `--chart-5` as grayscale (`oklch(x 0 0)`, zero chroma) from the `neutral` base preset — override `--chart-1` to the same value as `--primary` before wiring any chart. `--chart-2` through `--chart-5` stay unused; every chart in this phase is single-series, so a 5-hue categorical ramp is never needed (per the dataviz "never rainbow a single series" rule) |
| Destructive | `--destructive` red (`oklch(0.577 0.245 27.325)` light / `oklch(0.704 0.191 22.216)` dark) | The "Perdidos" KPI stat number + its small `TrendingDown` icon (reused meaning from Phase 2's "perdido" status badge), and the inline error banner if a dashboard fetch fails |
| **Success (reused from Phase 2, status-only)** | `green-600` `oklch(0.627 0.194 149.214)` light / `green-500` `oklch(0.723 0.219 149.579)` dark | The "Ganhos" KPI stat number + its small `TrendingUp` icon (reused meaning from Phase 2's "ganho" status badge) |

Accent reserved for: "Aplicar período" button, input/button focus rings, and every chart bar fill (via `--chart-1`). **Never** used for: the "Perdidos"/"Ganhos" stat numbers (those use Destructive/Success respectively), the "Taxa de conversão" stat number (neutral foreground ink — no defined threshold makes a conversion rate inherently "good" or "bad" without a target this phase doesn't specify, so it stays un-colored text), or any chart axis/tooltip text (per the dataviz rule "text never wears the data color" — labels and tick values stay in `--foreground`/`--muted-foreground`, only the bar mark itself carries blue).

## Screen-Specific Notes

### Dashboard (`app/(app)/dashboard/page.tsx`) — new nav item, separate from the kanban landing screen (D-03)

- Nav entry: "Dashboard" link added to `app/(app)/layout.tsx`'s existing nav, visible to both roles (unlike "Configurações"/"Gerenciar equipe", which stay Supervisor-only). The kanban (`/clientes`) remains the post-login landing screen — this nav item does not change that.
- Page-level Display heading "Dashboard" (28px/600), top-left, with the role-aware subtitle (Meta/help role, 14px/400, muted-foreground) directly beneath it.
- Period filter row, directly below the heading/subtitle (`md` gap): a `Select` (Claude's discretion, confirmed here) with the 4 preset options; choosing "Personalizado" reveals a `Popover` trigger button (same composition already used twice in `ClienteDetailSheet.tsx` for single-date pickers, extended to `mode="range"` per RESEARCH.md Pattern 6) containing a `Calendar` with `numberOfMonths={2}` and the "Aplicar período"/"Cancelar" footer. Selecting a preset applies immediately (no separate confirm step); only the custom range needs an explicit "Aplicar período" click, since a half-selected range isn't yet a valid filter value.
- Below the period filter (`lg` gap), the chart blocks in this fixed order:
  1. **"Clientes por etapa do funil"** — full-width `Card`. `Heading` title + Meta caption ("Situação atual — não é afetado pelo filtro de período") in the `CardHeader`. `CardContent` holds a vertical `BarChart` (RESEARCH.md Pattern 5), `h-[280px] w-full`, `accessibilityLayer` enabled, x-axis labels sourced from the existing `lib/funil/etapas.ts` label map (do not hardcode a second etapa→label lookup), single blue bar fill via `--chart-1`. Placed first, above the period-filtered content, specifically so its "always current, not filtered" nature reads as a deliberate opening orientation rather than a bug once the user later changes the period filter and this chart visibly doesn't react.
  2. **KPI row** — 3 `Card`s in a `md`-gapped 3-column grid (desktop) / stacked (mobile), `lg` internal padding each: "Ganhos" (Success green Stat number + `TrendingUp` icon), "Perdidos" (Destructive red Stat number + `TrendingDown` icon), "Taxa de conversão" (neutral-ink Stat number + `Percent` icon, muted-foreground). All 3 respect the period filter (D-02).
  3. **"Desempenho por vendedor"** (Supervisor-only, D-07 — omitted entirely for Vendedor, not shown disabled/blank, mirroring the existing `profile?.role === "supervisor"` conditional already used for "Gerenciar equipe"/"Configurações" nav links) — full-width `Card`, horizontal `BarChart` (RESEARCH.md Pattern 4), one bar per vendedor plotting their ganho count for the selected period, sorted descending (highest first). Height per the variable-row-count spacing exception above (grows with team size, caps at 480px + scroll).
  4. **"Prospecção por produto"** + **"Prospecção por categoria"** — 2-column grid (desktop) / stacked (mobile), each a `Card` with a horizontal `BarChart` (Pattern 4), height per the variable-row-count exception (bounded by Phase 3's editable lists, which can grow). Both filtered by `clientes.criado_em` within the selected period, per D-09/Assumption A1.
- Every chart/KPI card fetches and fails independently — a fetch error on "Desempenho por vendedor" shows that card's own error/retry state without blanking the "Clientes por etapa" chart above it (per the Error state copy above).
- A Vendedor's dashboard renders every block except "Desempenho por vendedor" — because every aggregate is RLS-scoped server-side (RESEARCH.md's SECURITY INVOKER pattern), a Vendedor's "Ganhos"/"Perdidos"/"Clientes por etapa"/"Prospecção" numbers are already narrowed to their own clientes with zero extra frontend filtering logic; the UI-level omission of the vendedor-breakdown chart is a UX nicety on top of that boundary, never the boundary itself.
