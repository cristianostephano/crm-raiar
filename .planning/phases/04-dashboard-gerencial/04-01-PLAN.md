## Phase Goal

**As a** supervisor ou vendedor, **I want to** enxergar a saúde do funil em números na medida da minha própria visão, **so that** eu tenha a informação gerencial que faltava para largar o CRM pago atual.

> This plan delivers the phase's data foundation and proves the core capability end-to-end via tests: a real Vendedor session gets only its own numbers, a Supervisor gets the whole team. Waves 2-4 make those numbers visible on screen.

<objective>
Build the entire read-only aggregation backend for the Dashboard Gerencial: 5 `language sql stable` (SECURITY INVOKER) Postgres functions that each aggregate over the already-RLS-scoped `clientes`/`historico`/`cliente_produtos` tables, their typed query + Server Action wrappers, the pure period-math utility, and a full behavior + RLS test suite. No new tables, no mutations — this is purely a read layer over data Phases 2-3 already produce.

Purpose: The dashboard's numbers must be computed inside Postgres (per CLAUDE.md's egress constraint — never a client-side reduction over a full client list) and must be RLS-scoped per caller so a Vendedor physically cannot retrieve another vendedor's aggregates, even by calling the RPC directly (DSH-06/DSH-07/D-07).
Output: `0003_dashboard_aggregates.sql` (pushed), `lib/dashboard/periodo.ts`, `lib/supabase/queries/dashboard.ts`, `app/actions/dashboard.ts`, 6 test files under `tests/dashboard/`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (browser) → Supabase RPC | An authenticated Vendedor or Supervisor invokes the dashboard functions; the caller's identity and role are the only inputs the DB trusts. |
| Server Action → Postgres function | Period `Date` values cross as typed `timestamptz` RPC parameters. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information Disclosure | dashboard_* functions over clientes/historico | high | mitigate | Invoker-rights functions (no privilege escalation) → existing clientes/historico RLS scopes every result to the caller's own rows; proven by tests/dashboard/rls-dashboard.test.ts (Vendedor B sees zero of Vendedor A's aggregates). |
| T-04-02 | Elevation of Privilege | future edit adding a DEFINER clause | high | mitigate | Header comment on every function forbidding the escalation clause + the RLS test fails loudly if one is ever added (Pitfall 4). |
| T-04-03 | Tampering | p_inicio/p_fim RPC parameters | low | mitigate | supabase.rpc() binds them as typed timestamptz parameters — never string-concatenated into SQL, so no injection surface. |
</threat_model>
