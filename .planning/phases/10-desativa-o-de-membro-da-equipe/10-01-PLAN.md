<objective>
Create the entire database foundation for deactivating a team member, and prove it landed in the live database.

This plan adds one column (`profiles.ativo`), extends one existing helper (`is_supervisor()`), and creates two new `SECURITY DEFINER` RPCs (`desativar_membro_equipe`, `reativar_membro_equipe`) in a single new migration file. It implements D-01 (a Supervisor can never deactivate their own account) and D-02 (reactivation is possible and deliberately low-friction) at the database level, and delivers the reassignment rule behind EQP-01/EQP-04 (only `em_andamento` clientes move to the substitute; `ganho`/`perdido` stay with the deactivated member).

Purpose: every other plan in this phase (tests, Server Actions, UI) is blocked until these four objects exist in the live hosted database. RLS is this project's only authorization boundary, so this is where EQP-02 and EQP-03 are actually enforced — not in the UI.
Output: `supabase/migrations/0008_desativacao_membro_equipe.sql` applied to the live database, plus a smoke test that fails loudly if the push never happened.
</objective>

Write four sections, in this order:

Section 1 — add the column: `alter table profiles add column ativo boolean not null default true;`. The `default true` is what guarantees every existing member stays active after the push.

Section 2 — replace `is_supervisor()` with `create or replace function`, keeping its existing signature and modifiers exactly (`returns boolean`, `language sql`, `security definer`, `set search_path = public`, `stable`), adding one condition to the existing `exists` subquery so it requires `role = 'supervisor'` AND `ativo = true` for `id = (select auth.uid())`. Add a comment stating that this single change cascades to every existing RLS policy that already calls `is_supervisor()`, with zero policy edits, and that this is the primary EQP-03 enforcement because RLS re-evaluates on every request.

Section 3 — create `desativar_membro_equipe(p_profile_id uuid, p_novo_responsavel_id uuid) returns table(clientes_reatribuidos bigint)`, `language plpgsql`, `security definer`, `set search_path = public`. Declare `v_target_role user_role` and `v_reatribuidos bigint`. Body, in exactly this order:
  1. `if not is_supervisor() then raise exception 'Somente supervisores podem desativar membros da equipe';` — this must be the literal first statement of the function body. Add a comment stating why this function is `security definer` at all: `profiles` has zero write policies by design, so a non-definer RPC's internal update would affect zero rows; this is the second documented exception in this codebase, after `is_supervisor()` itself.
  2. D-01 self-deactivation guard: `if p_profile_id = (select auth.uid()) then raise exception 'Não é possível desativar a própria conta';`.
  3. `select role into v_target_role from profiles where id = p_profile_id;` then `if v_target_role is null then raise exception 'Membro não encontrado';`.
  4. Substitute validation: `if not exists (select 1 from profiles where id = p_novo_responsavel_id and ativo = true) then raise exception 'Vendedor substituto inválido ou inativo';`. Comment that this defensive check is required precisely because `security definer` bypasses RLS, so the caller's own scoping cannot be trusted.
  5. EQP-02 last-active-Supervisor guard, only when `v_target_role = 'supervisor'`: first `perform 1 from profiles where role = 'supervisor' and ativo = true for update;` to take the row lock, THEN `if (select count(*) from profiles where role = 'supervisor' and ativo = true and id <> p_profile_id) < 1 then raise exception 'Não é possível desativar o último Supervisor ativo';`. The lock must come before the count — that ordering is the whole TOCTOU mitigation.
  6. EQP-01/EQP-04 reassignment as its own top-level statement: `update clientes set responsavel = p_novo_responsavel_id where responsavel = p_profile_id and status_acompanhamento = 'em_andamento';` immediately followed by `get diagnostics v_reatribuidos = row_count;`.
  7. Deactivation as a separate top-level statement: `update profiles set ativo = false where id = p_profile_id;`.
  8. `return query select v_reatribuidos;`.
Steps 6 and 7 must remain two independent top-level statements inside the same plpgsql transaction. They are already atomic that way; merging them into one data-modifying statement chain would reintroduce the exact same-snapshot visibility defect this repository already had to fix in migration 0006. The `get diagnostics` line in step 6 is the structural proof they stayed separate.

Section 4 — create `reativar_membro_equipe(p_profile_id uuid) returns void`, `language plpgsql`, `security definer`, `set search_path = public`. Body: the same `if not is_supervisor() then raise exception 'Somente supervisores podem reativar membros da equipe';` as the literal first statement, then `update profiles set ativo = true where id = p_profile_id;`. Add a comment recording D-02: no last-Supervisor guard and no self-guard apply in this direction, because reactivating strictly adds capacity back; two separate RPCs (not one branching RPC with a boolean parameter) because the guard logic genuinely differs.

Do NOT add an UPDATE policy on `profiles` — a Supervisor-scoped UPDATE policy would open every column including `role` to direct client writes. Do NOT add an `is_ativo()` helper and do NOT touch the Vendedor branch of the `clientes`/`tarefas`/`historico` policies: the residual window in which a deactivated Vendedor's still-valid token can still read their own already-closed clientes was presented to the project owner and explicitly accepted as-is. It is out of scope for this phase.
