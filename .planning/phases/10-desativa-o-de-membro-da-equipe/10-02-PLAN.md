<objective>
Build the disposable-member test fixture this phase needs, and prove the reassignment contract behind EQP-01 and EQP-04 against the live database.

This plan delivers the Wave 0 items from `10-VALIDATION.md`: a fixture helper that creates and tears down throwaway team members (needed because every deactivation test permanently flips a real `profiles` row, so no test may ever target a shared seed account), and `tests/equipe/reassignment.test.ts`, which is the only automated proof that the reassignment `WHERE status_acompanhamento = 'em_andamento'` filter written in 10-01 actually behaves as the product decision requires.

Output: an extended `tests/helpers/supabase-test-clients.ts`, a new `tests/equipe/reassignment.test.ts`, and a narrowed assertion in 10-01's smoke test so disposable fixtures cannot make it flaky.
</objective>

Step 1 — extend `tests/helpers/supabase-test-clients.ts` (append below `signInAs`, change nothing above it).

Export a type `TestMember` with fields `id: string`, `email: string`, `password: string`, `nome: string`, `sobrenome: string`.

Export `async function createTestMember(role: "supervisor" | "vendedor", label?: string): Promise<TestMember>`. It generates a unique email of the form `equipe-fixture-{label ?? role}-{Date.now()}-{6 random base36 chars}@raiar.local`, uses the constant password `TestEquipeFixture!2026`, and calls `serviceClient().auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { nome, sobrenome, celular, role } })`. `email_confirm: true` is mandatory — without it the fixture cannot sign in, which the EQP-03 test in plan 10-03 depends on. The `user_metadata` keys are not free-form: `handle_new_user` reads exactly `nome`, `sobrenome`, `celular` and `role` out of `raw_user_meta_data` and inserts them into NOT NULL columns, so all four must be present and `role` must be one of the two `user_role` enum values. Use `nome = "Fixture"`, `sobrenome` = the unique suffix (so two fixtures never render identically in a UI or a failure message), and `celular = "11999990000"` (same throwaway shape already used by `baseRowFields` in `tests/importacao/rls-importar-lote.test.ts`). If `createUser` returns an error, throw with the message included — silent fixture failures produce confusing downstream assertion errors. Return the `TestMember`, taking the id from the created user.

Export `async function deleteTestMember(id: string): Promise<void>` calling `serviceClient().auth.admin.deleteUser(id)`. Document in a comment directly above it that `clientes.responsavel` references `profiles(id)` with no ON DELETE action, so every cliente seeded for this member must be deleted first or this call fails with a foreign-key violation; and that the `profiles` row itself needs no explicit delete because `profiles.id` cascades from `auth.users`.

Write a short header comment above both, naming Phase 10 and stating why disposable members exist at all: deactivation permanently flips a real `profiles` row, so a test must never target `SEED_ACCOUNTS.vendedorA/B` or the seeded Supervisor — those are shared across every phase's suites.

Add a one-line comment explaining that the assertion is deliberately scoped to the seeded accounts because disposable `equipe-fixture-` members may legitimately be inactive mid-run. Change nothing else in that file — the other three assertions stay exactly as 10-01 wrote them.

Create `tests/equipe/reassignment.test.ts`. File-header comment: this suite is the executable form of the locked product rule that only in-progress business moves to the substitute (EQP-01) while already-won and already-lost clientes stay credited to the deactivated member (EQP-04) — a rule that has no UI surface and would regress invisibly.

Shared setup, run inside each test (or a `beforeAll`/`afterAll` pair, whichever keeps cleanup unconditional):
  - `const alvo = await createTestMember("vendedor", "alvo")` — the member who gets deactivated. Never use a `SEED_ACCOUNTS` identity as the target.
  - The substitute is `SEED_ACCOUNTS.vendedorA`; get its uuid the same way `rls-importar-lote.test.ts` does (`signInAs` then `auth.getUser()`).
  - Read one `motivos_perda` id via `serviceClient().from("motivos_perda").select("id").limit(1).single()`.
  - Seed three clientes via `serviceClient().from("clientes").insert(...)`, all with `responsavel = alvo.id` and unique razão social: (a) an in-progress one, leaving `etapa` and `status_acompanhamento` at their column defaults (`aguardando_contato` / `em_andamento`); (b) a won one with `etapa: "primeira_venda"` and `status_acompanhamento: "ganho"`; (c) a lost one with `status_acompanhamento: "perdido"` and `motivo_perda_id` set to the id read above. Collect all three ids for cleanup.

Test 1 — its name MUST contain the exact substring `reassigns em_andamento`, because `10-VALIDATION.md` pins the command `npx vitest run tests/equipe/reassignment.test.ts -t "reassigns em_andamento"`. Sign in as `SEED_ACCOUNTS.supervisor` and call `rpc("desativar_membro_equipe", { p_profile_id: alvo.id, p_novo_responsavel_id: <vendedorA uuid> })`. Assert `error` is null; assert the returned row's `clientes_reatribuidos` equals 1 (the RPC returns a table, so read `data[0].clientes_reatribuidos`; note Supabase returns `bigint` as a number or a numeric string depending on the driver — compare with `Number(...)` to stay robust). Then read the in-progress cliente back with `serviceClient()` and assert its `responsavel` is now the vendedorA uuid. Also assert `profiles.ativo` for `alvo.id` is now `false`, read back with `serviceClient()`.

Test 2 — its name MUST contain the exact substring `preserves closed`. Against the same post-deactivation state (or a fresh fixture set if each test seeds its own), read the won and the lost cliente back with `serviceClient()` and assert BOTH still have `responsavel === alvo.id`. Assert explicitly, per cliente, so a failure message names which one moved.

Cleanup discipline: delete the three seeded clientes with `serviceClient()` FIRST, then call `deleteTestMember(alvo.id)`. The reverse order fails on the `clientes.responsavel` foreign key. Put the cleanup somewhere that runs even when an assertion throws (an `afterAll`, or a try/finally), otherwise a failed run leaves a permanently deactivated ghost member in the live team list — which the Supervisor would then see on the real "Gerenciar equipe" screen.

Do not use `serviceClient()` for the RPC call itself: the service role bypasses RLS and `is_supervisor()`, so the call would pass regardless of the guards and prove nothing (same discipline documented in `rls-importar-lote.test.ts`'s header).

## Trust Boundaries

|----------|-------------|
| test process -> live hosted database | These suites write real rows into the real project; a failed teardown leaves real, visible data behind |
| `serviceClient()` -> RLS | The service role bypasses RLS entirely; using it for an assertion would make the assertion meaningless |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-10-10 | Tampering | test fixtures against the live project | medium | mitigate | Disposable members only (`equipe-fixture-` emails), never a `SEED_ACCOUNTS` identity as the deactivation target; cleanup runs unconditionally (afterAll / try-finally), clientes deleted before the member |
| T-10-11 | Spoofing | RPC call under test | high | mitigate | The RPC is invoked through `signInAs(SEED_ACCOUNTS.supervisor)`, never through `serviceClient()`, so `is_supervisor()` is genuinely exercised rather than bypassed |
