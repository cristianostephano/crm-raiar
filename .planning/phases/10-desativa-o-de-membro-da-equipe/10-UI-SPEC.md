# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase extends the existing "Gerenciar equipe" table (`app/(app)/equipe/page.tsx`) with a Status column (Ativo/Inativo badge) and a per-row Desativar/Reativar action, plus a new confirmation dialog (`DesativarMembroDialog`) that always asks the Supervisor to pick a replacement vendedor (D-03) before deactivating a member. No new screen, no new type scale, no new color, and no new shadcn component is introduced — every token below is reused exactly from Phase 8/9's approved UI-SPECs, and the interaction shape (Dialog for the destructive-feeling action, no-dialog one-click reversal) is copied verbatim from `components/configuracoes/EditableListTab.tsx`'s already-shipped, already-reviewed precedent (RESEARCH.md Pattern 3). See "Component-Specific Implementation Notes" for the exact behavior this phase's contract mostly lives in.

## Component-Specific Implementation Notes

*(Extends the template — per RESEARCH.md's Recommended Project Structure, this lands as `components/equipe/EquipeList.tsx` (Client Component, row actions + Status badge) and `components/equipe/DesativarMembroDialog.tsx` (replacement picker + confirm), consumed by the existing `app/(app)/equipe/page.tsx`.)*

### 1. Table structure — new "Status" column + new "Ações" column

- Column order: **Nome | Sobrenome | Papel | Status | E-mail | Ações** — Status is inserted immediately after Papel (keeps role/status semantically grouped); Ações is always the last column, matching every other action-column convention in this app (e.g. `ClienteDetailSheet`'s footer action placement).
- Status column renders the `Badge variant="outline"` described in Copywriting Contract — "Ativo" or "Inativo" — for every row, always visible (unlike `EditableListTab`, which only badges the inactive case; this phase's explicit scope item 1 requires a visible indicator for both states).
- Ações column renders exactly one icon button per row:
  - `ativo === true` → "Desativar" (`EyeOff` icon, `variant="ghost"`, `size="icon"`) — **except** on the row belonging to the currently logged-in Supervisor (`member.id === session user id`), where no action renders at all (render a plain `—` or leave the cell empty) — this is the primary UI-level control for D-01's self-deactivation block; the RPC's own guard (Copywriting Contract's self-deactivation error string) is defense-in-depth only, for the case where this client-side hiding is ever bypassed or stale.
  - `ativo === false` → "Reativar" (`Eye` icon, `variant="ghost"`, `size="icon"`, disabled while that row's request is in flight) — no dialog, fires `reativarMembroEquipe` directly on click, exactly mirroring `EditableListTab.reactivate()`'s `reactivatingId` in-flight-disable pattern.
- **Do not** hide the Desativar action for a row that happens to be the last active Supervisor — unlike the self-deactivation case, this guard is a `SELECT ... FOR UPDATE`-gated aggregate count inside the RPC (RESEARCH.md Pitfall A, TOCTOU-safe), and replicating that count client-side to decide whether to render the button would reintroduce exactly the race condition the backend guard exists to close. Let the click proceed; surface the RPC's error inline in the dialog instead (Copywriting Contract's last-Supervisor error string).

### 2. `DesativarMembroDialog` — replacement picker, always shown (D-03)

- Opens via the row's "Desativar" button. Structure: `DialogHeader`/`DialogTitle` ("Desativar {nome} {sobrenome}?") → consequence paragraph (Copywriting Contract, `text-sm text-muted-foreground`, same treatment as `ClienteDetailSheet`'s delete-confirmation paragraph) → `Select` for "Vendedor substituto" (required, no "nenhum" sentinel — matches the required-field convention already used for "Responsável" in `ClienteDetailSheet.tsx`) → inline error area (`role="alert"`, `text-destructive`, appears below the Select or below the whole form depending on error type) → `DialogFooter` with "Cancelar" (`variant="ghost"`) / "Desativar" (`variant="secondary"`, disabled while submitting, label switches to "Desativando...").
- **Replacement picker options:** active Vendedores only (`role = 'vendedor' and ativo = true`), per RESEARCH.md's Open Question 3 recommendation — restricting the picker's options is a UI-level convenience matching the product framing "vendedor substituto" literally; it is not a substitute for the RPC's own defensive `ativo = true` check on the chosen id (RESEARCH.md Pattern 1), which remains the actual trust boundary.
- **D-03 — always shown, no conditional branching:** the dialog and its required Select render identically whether or not the target member currently has any `em_andamento` clientes to transfer. Do not add a "this vendedor has no active clients, skip the picker" branch — this is an explicit, locked product decision, not an oversight.
- **Validation order inside the dialog, exactly matching this priority:** (1) client-side "nothing picked yet" check blocks the Desativar button's `onClick` handler from calling the Server Action at all (cheapest, fastest feedback) → (2) Server Action / RPC-level errors (self-deactivation, last-Supervisor, invalid replacement, generic, partial ban-failure) render inline in the same error area, using the exact strings from the Copywriting Contract, each mapped from the Server Action's returned `error.code` the same way `ClienteDetailSheet.onSubmit` already maps `duplicate_razao_social` vs. a generic fallback.
- On success: close the dialog, flip that row's Status badge to "Inativo" and re-render its Ações cell as "Reativar" (or empty, if it happens to be the caller's own row — not reachable in practice since D-01 already hides the action there), and show the success banner (Copywriting Contract) above the table — same transient-banner placement and styling as `EditableListTab`'s `successMessage`.

### 3. Reativar — no dialog (D-02)

- Single click on the row's "Reativar" `Eye` icon button calls `reativarMembroEquipe(profileId)` directly — no confirmation step, matching `EditableListTab.reactivate()` exactly (already the established, reviewed pattern for the "low-friction reversible" framing in this project, per `STATE.md`'s Phase 3 decision log).
- While in flight: disable that specific row's Reativar button only (track by `profileId`, mirroring `EditableListTab`'s `reactivatingId` state — never a page-wide loading lock).
- On success: flip the row's Status badge to "Ativo", swap the Ações cell to "Desativar" (unless it's the caller's own row scenario, not reachable here), show the success banner.
- On failure: show the generic reativar error string (Copywriting Contract) in the same transient banner area used for the form's `formError`, matching `EditableListTab`'s top-level error banner placement (not a per-row inline error, since there's no dialog to anchor it to).

### 4. Anti-Patterns to avoid (specific to this phase's UI)

- Do not color-code the Status badge (no green "Ativo" / red "Inativo") — both render with the same neutral `variant="outline"` treatment; color is reserved exclusively for the roles listed in the Color section (accent = success banner + Convidar button; destructive = error text only).
- Do not use `variant="destructive"` on the dialog's "Desativar" confirm button — this project's own precedent (`EditableListTab`) deliberately keeps deactivation actions on `variant="secondary"` since D-02 frames every deactivation in this app as reversible, not permanent.
- Do not add a branch that skips or shortens the replacement-picker dialog when the target has zero `em_andamento` clientes (D-03) — the dialog's shape must stay identical regardless of how many clientes would actually be reassigned.
- Do not attempt to replicate the last-active-Supervisor count client-side to decide whether to show/hide the Desativar button for a Supervisor row — only the self-deactivation case (a simple identity comparison, not a race-prone aggregate count) is safe to gate client-side.
