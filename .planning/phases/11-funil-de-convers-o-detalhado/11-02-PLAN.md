<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client Component → Server Action | Chamada vinda do browser cruza para o servidor; a action é o primeiro ponto que valida sessão. |
| Server Action → RPC do Postgres | A sessão do usuário logado é propagada pelo cookie, e é ela que a RLS usa para filtrar. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-05 | Spoofing / Information Disclosure | `getFunilDetalhadoAction` / `getTempoAteFechamentoAction` | high | mitigate | Guard `supabase.auth.getUser()` antes de qualquer leitura, devolvendo `"unauthenticated"` quando não houver sessão — mesmo formato das cinco actions existentes. A defesa real continua sendo a RLS nas RPCs (plano 01): mesmo se o guard fosse removido, um chamador sem sessão não veria linha nenhuma. |
| T-11-06 | Information Disclosure | mensagem de erro devolvida ao browser | low | mitigate | O `catch` é genérico e nunca propaga `error.message` do Postgres para o cliente — devolve a string fixa `"Não foi possível carregar os dados do dashboard. Tente novamente."`, exatamente como as actions existentes, evitando vazar nome de tabela/coluna ou detalhe de query. |
| T-11-07 | Elevation of Privilege | filtro de papel implementado no TypeScript | medium | mitigate | Proibido por design: nenhuma das funções novas filtra por `responsavel` ou papel. O CLAUDE.md exige que a autorização viva na RLS; qualquer filtro em TS seria uma segunda fonte de verdade capaz de divergir. Coberto pelo check de aceite e pelo teste de RLS do plano 01. |
| T-11-SC | Tampering (supply chain) | instalação de pacotes | low | accept | Nenhum `npm install` neste plano. |
</threat_model>
