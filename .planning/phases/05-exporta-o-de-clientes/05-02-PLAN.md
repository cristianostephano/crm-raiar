    Create app/api/clientes/exportar/route.ts as a POST Route Handler, using app/auth/confirm/route.ts as the structural analog (parse request, call an existing lib/supabase helper, return a NextResponse). Set `export const runtime = "nodejs"` — @e965/xlsx needs Node Buffer APIs and must not run on Edge (STACK.md v1.1 Addendum). This is the one sanctioned app/api handler in the app (ARCHITECTURE.md Pattern 6): it exists only because forcing a file download needs Content-Disposition/Content-Type headers a Server Action cannot set — it introduces NO new authorization logic.

    Because this route sits under app/api (outside the app/(app)/layout.tsx auth guard), re-check auth itself: await createClient(), call supabase.auth.getUser(), and if there is no user return a 401 NextResponse (do not redirect — this is a fetch target, not a navigated page). This mirrors the redirect("/login") gate in app/(app)/clientes/page.tsx, adapted to a Route Handler.

    Parse the body with await request.json() and read `ids`. Validate that ids is an array of strings; if the body is missing or ids is not a string array, return a 400 NextResponse. An empty array is valid (it yields a header-only workbook — harmless). Do NOT trust ids as an authorization input: pass it to getClientesParaExportacao(ids), whose RLS scoping (EXP-01/EXP-02) is the real boundary — any id the caller cannot see returns 0 rows for it, the same non-revealing posture as getClienteById.

    Call getClientesParaExportacao(ids) from lib/supabase/queries/clientes.ts, then buildClientesWorkbook(rows) from lib/clientes/exportacao.ts. Compute a filename like clientes_YYYY-MM-DD.xlsx from the current date (Claude's discretion per D-04's referenced discretion note). Return a new NextResponse(workbookBuffer) with header Content-Type set to the xlsx spreadsheet MIME (application/vnd.openxmlformats-officedocument.spreadsheetml.sheet) and Content-Disposition set to attachment with that filename (D-01: xlsx only). Wrap the query/build in a try/catch and return a 500 NextResponse on failure rather than throwing an unhandled error, consistent with the route-level error convention.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → POST /api/clientes/exportar | The `ids` array in the request body is attacker-controllable; a caller could POST arbitrary ids, including other vendedores'. |
| unauthenticated client → Route Handler | The route sits outside the (app)/layout auth guard, so it must gate auth itself. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03 | Information Disclosure | POST /api/clientes/exportar (ids body) | high | mitigate | ids is never an authorization input — getClientesParaExportacao is RLS-scoped, so ids the caller cannot see return 0 rows (non-revealing). A Vendedor cannot export another vendedor's clientes by guessing/passing their ids. Proven at the query layer by 05-01's RLS test and confirmed end-to-end in Task 3. |
| T-05-04 | Spoofing / DoS | Route Handler entry | medium | mitigate | Explicit supabase.auth.getUser() 401 gate for unauthenticated requests; ids validated as a string array (400 on malformed) before any query runs. Request body is JSON ids only (kilobytes at realistic volume, far under Vercel's 4.5MB body ceiling). |
| T-05-01 | Tampering | exported cell content | medium | mitigate | Formula-injection sanitization is enforced in buildClientesWorkbook (05-01, T-05-01); this plan only transports its output. Re-confirmed by Task 3's injection check. |
</threat_model>
