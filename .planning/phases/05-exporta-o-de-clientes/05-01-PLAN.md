<objective>
Build the two pure, independently-testable pieces the export feature stands on: the RLS-scoped read that fetches export-shaped cliente rows, and the dependency-free helper that turns those rows into a downloadable Excel workbook with formula-injection protection. Also install the one new dependency (`@e965/xlsx`) behind a package-legitimacy human gate.

Purpose: Export is the lowest-risk feature of the milestone (pure read, no RPC, no writes). Isolating the data layer here means EXP-01/EXP-02 (role scoping) and the D-02 column shape are proven by fast, deterministic tests before any endpoint or button exists.
Output: `getClientesParaExportacao` (query), `ClienteExportRow` (type), `buildClientesWorkbook` + `sanitizeCell` (xlsx helper), plus one RLS test and one unit test. The `@e965/xlsx` dependency added to `package.json`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored cliente data → exported .xlsx cell | Free-text fields (razão social, contato, observação) are user-entered and untrusted; they become executable if a spreadsheet app interprets a leading =/+/-/@ as a formula. |
| caller session → clientes read | Which rows a caller may export is decided entirely by RLS on `clientes`; the query must never widen that with its own logic. |
| npm registry → build | A new third-party dependency (`@e965/xlsx`) enters the dependency tree. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | buildClientesWorkbook cells (razão social/contato/observação) | medium | mitigate | sanitizeCell prefixes a leading apostrophe on any cell starting with =/+/-/@/tab/CR, applied to every string cell through one shared path (Pitfall A4 / success criterion 4); unit-tested. |
| T-05-02 | Information Disclosure | getClientesParaExportacao | high | mitigate | RLS on `clientes` (is_supervisor() OR responsavel = auth.uid()) is the only authorization boundary; `.in("id", ids)` is layered on top, never replaces it. RLS test proves a Vendedor cannot obtain another vendedor's rows even by passing their ids. |
| T-05-SC | Tampering | `npm install @e965/xlsx` | high | mitigate | Blocking-human package-legitimacy checkpoint (Task 1) verifies the package on npmjs.com before install; the plain vulnerable `xlsx` package is explicitly rejected. Not auto-approvable. |
</threat_model>
