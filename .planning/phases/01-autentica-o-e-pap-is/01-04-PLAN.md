<objective>
## Phase Goal (MVP user story)

**As a** sales-team member, **I want to** log in securely with my Supervisor or Vendedor role recognized system-wide, **so that** the database itself controls what I can see — starting at the data layer, not the screen.

## This plan

Deliver AUTH-02 end-to-end: the Supervisor-only "Gerenciar equipe" area where a Supervisor invites a new Vendedor or Supervisor. Because there is no public sign-up (D-01), account creation runs through `auth.admin.inviteUserByEmail`, which needs the service_role/secret key and sends an email — so it lives in a Supabase Edge Function, not a Next.js Server Action (per `supabase-conventions` and RESEARCH Pattern 2). The Edge Function independently re-checks that the caller is actually a Supervisor (D-10), the invite form makes the Supervisor pick the papel explicitly (D-05), and the screen redirects any non-Supervisor.

Purpose: This is the "Supervisor cadastra vendedor" slice — the second real round-trip of the walking skeleton. It closes AUTH-02 (create a user with email/nome/sobrenome/celular + role) and reinforces AUTH-03 (role distinction is enforced server-side, not hidden in the UI). The invited user then sets their own senha via the `/auth/confirm` callback + set-password page delivered in plan 05 — this plan proves the invite is sent and the account is created with the correct role.
Output: the `invite-user` Edge Function + its authorization test, the "Gerenciar equipe" page + invite form, and a Supervisor-only nav link.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (Supervisor) -> invite-user Edge Function | A role-elevating account-creation action crosses here |
| any authenticated client -> invite-user HTTP endpoint | The endpoint is publicly reachable with ANY valid JWT (verify_jwt proves authentication, not Supervisor authority) |
| Edge Function -> Supabase Auth admin API | The service_role/secret key privilege lives only in the Deno runtime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Elevation of Privilege | invite-user Edge Function authorization | critical | mitigate | The function reads the CALLER's own `profiles.role` via their JWT-scoped client and returns 403 for non-Supervisors BEFORE building the service_role admin client (RESEARCH phase-specific pitfall). `tests/auth/invite.test.ts` asserts Vendedor -> 403 |
| T-01-11 | Elevation of Privilege | `role` field in the request body | high | mitigate | The body `role` only sets the NEW user's role (chosen by an already-verified Supervisor, D-05); it is never used to authorize the caller — caller authority comes solely from the server-side `profiles.role` lookup |
| T-01-12 | Information Disclosure | service_role/secret key in the Edge Function | high | mitigate | Secret key read only via `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')` inside the Deno runtime; never in a `NEXT_PUBLIC_*` var or any client-bundled module (Pattern 2) |
| T-01-13 | Tampering | invite input (email / role / fields) | medium | mitigate | The Edge Function re-validates the body with zod server-side (email format, role in the `user_role` enum) after the 403 gate — never trusts the client payload (ASVS V5) |
| T-01-14 | Spoofing | client-side Supervisor-only nav link + `/equipe` redirect | medium | accept | The redirect and Supervisor-gated nav link are UX only; a Vendedor bypassing them still hits the Edge Function's 403 and RLS — the app-layer gate is intentionally not the boundary (CLAUDE.md rule) |
| T-01-15 | Tampering | Deno `jsr:@supabase/supabase-js@2` import in the Edge Function | low | accept | Official Supabase package pinned to major 2 on the JSR registry; no new npm install is introduced by this plan (npm supply-chain gate was handled in plan 01) |
</threat_model>
