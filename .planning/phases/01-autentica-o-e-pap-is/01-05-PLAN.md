## Phase Goal (MVP user story)

**As a** sales-team member, **I want to** log in securely with my Supervisor or Vendedor role recognized system-wide, **so that** the database itself controls what I can see — starting at the data layer, not the screen.

## This plan

Deliver password recovery (D-08) and complete the account-creation loop opened by plan 04. Build the single `/auth/confirm` callback route that exchanges an email token (`verifyOtp`) and starts a session — this one route serves BOTH the invite link (plan 04's `redirectTo`) and the password-reset link (RESEARCH: "one callback route serves both"). Build the "Esqueci minha senha" page (calls `resetPasswordForEmail`) that the login screen from plan 03 already links to, and the "Salvar nova senha" page (calls `auth.updateUser`) that both an invited user (setting their initial senha, D-02) and a recovery user (setting a new one, D-08) land on after the token exchange.

Purpose: This closes the two email-based flows of the phase. It satisfies AUTH-01's password-recovery half (D-08, mapped to AUTH-01 in VALIDATION.md's Manual-Only table) and finishes AUTH-02 — the invited user actually sets their own senha here, which is the "senha" field of AUTH-02's user record (the Supervisor never knows it, D-02). Because the invite link and the reset link both flow through this plan's `/auth/confirm`, the final human checkpoint verifies both round-trips through the one route (hence this plan depends on plan 04).
Output: the shared `/auth/confirm` Route Handler, the forgot-password page + form, the reset-password page + form, and a password-change contract test.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email link (token) -> /auth/confirm route | The one-time token is exchanged for a session here |
| browser -> Supabase Auth (resetPasswordForEmail / updateUser) | Credential-recovery and password-change requests cross here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-16 | Spoofing / Information Disclosure | invite / reset token reuse or interception | high | mitigate | Rely on Supabase Auth's own `verifyOtp` single-use + expiry semantics; no custom token scheme (RESEARCH Security Domain). The token exchange happens server-side in the `/auth/confirm` Route Handler via the SSR client |
| T-01-17 | Information Disclosure | forgot-password email enumeration | medium | mitigate | The non-revealing success copy is shown regardless of whether the email exists (UI-SPEC Copywriting Contract) — it does not disclose account existence |
| T-01-18 | Elevation of Privilege | setting a new password without a confirmed session | high | mitigate | `reset-password`'s `updateUser` requires the active session that `/auth/confirm`'s `verifyOtp` establishes; without a valid confirmed session the password change fails. Server contexts validate via `getUser`, never an unrefreshed cookie |
| T-01-19 | Tampering | new-password input | low | mitigate | zod min-length validation client-side; Supabase Auth enforces its own password policy server-side |
</threat_model>
