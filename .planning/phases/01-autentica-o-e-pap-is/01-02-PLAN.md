<objective>
## Phase Goal (MVP user story)

**As a** sales-team member, **I want to** log in securely with my Supervisor or Vendedor role recognized system-wide, **so that** the database itself controls what I can see — starting at the data layer, not the screen.

## This plan

Create the authorization backbone the entire project stands on: the `profiles` table, the `user_role` enum, RLS enabled with a SELECT policy, the `is_supervisor()` `SECURITY DEFINER` helper every later RLS policy will call, and the `handle_new_user()` trigger that syncs invite metadata into `profiles`. Then apply the migration to the real hosted project ([BLOCKING] `supabase db push`), seed the first Supervisor (D-03 — real owner email, asked at execution time) plus two Vendedor test accounts (RESEARCH Pitfall 2), and prove cross-role isolation with an automated test.

Purpose: This is the walking skeleton's real DB read/write. Every RLS policy in phases 2–5 copies the `is_supervisor()` + `(select auth.uid())` conventions established here (D-06: works for any number of Supervisors). No `UPDATE`/`DELETE` policy is created — editing an existing profile's role/data is explicitly out of scope (D-07).
Output: `supabase/migrations/0001_profiles_and_roles.sql`, `supabase/seed/seed-users.mjs`, `tests/auth/rls-roles.test.ts`, and the migration applied to the hosted Supabase project.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client -> Postgres (RLS) | Any authenticated user (incl. a Vendedor) can issue arbitrary queries with the public key; RLS is the only gate |
| service_role seed script -> auth.users | Privileged account creation bypasses RLS; runs server-side only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-03 | Information Disclosure | `profiles` RLS | critical | mitigate | RLS enabled in the same migration as the table + SELECT policy; verified via `relrowsecurity` query (Pitfall 1). SELECT policy is intentionally read-all (team list needs it); no sensitive per-user secret lives in `profiles` |
| T-01-04 | Tampering | `profiles.role` self-elevation | high | mitigate | No UPDATE/DELETE policy exists for regular users; role is only ever written by the `SECURITY DEFINER` trigger from invite metadata (D-07 out of scope for role edits). RLS test asserts a Vendedor UPDATE affects zero rows |
| T-01-05 | Denial of Service | RLS recursion on `profiles` | high | mitigate | `is_supervisor()` is `SECURITY DEFINER` so its internal lookup bypasses RLS, preventing the recursive-policy hang (RESEARCH Pattern 1) |
| T-01-06 | Elevation of Privilege | seed script secret key | high | mitigate | Secret key read only inside the Node seed script (server context), never in a `NEXT_PUBLIC_*` var or client bundle |
</threat_model>
