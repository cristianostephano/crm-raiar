# Phase 1 — UI Design Contract

> Visual and interaction contract for Autenticação e Papéis (login, "esqueci minha senha", and the Supervisor-only "gerenciar equipe" screen). This is the FIRST UI-SPEC in the project — it establishes the design-system foundation every later phase's UI-SPEC inherits. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (initialized this phase — `components.json` created, previously absent) |
| Preset | `nova` (`base-nova` style, `baseColor: neutral`, css variables on) |
| Component library | radix primitives via `@base-ui/react` (shadcn "base" library) |
| Icon library | `lucide-react` (already locked in project's stack, ^1.24.0) |
| Font | Geist Sans (body/UI), Geist Mono (code/monospace) — via `next/font/google`, already present in the `create-next-app` skeleton. Fixed a shadcn-CLI init bug where `--font-sans` self-referenced instead of pointing to `--font-geist-sans`; corrected in `app/globals.css`. |

**Color decision (confirmed by user this session):** Background white/light-gray, text dark-gray/near-black, **blue is the single accent color** — reserved only for primary buttons and active/selected states. Red only for destructive/error situations. This overrides shadcn's `neutral` preset default (which ships a grayscale/black `--primary`) — `--primary`, `--ring`, `--sidebar-primary`, and `--sidebar-ring` were manually set to blue (`oklch(0.546 0.215 262.881)` light / `oklch(0.623 0.188 259.815)` dark, ≈ Tailwind `blue-600` / `blue-500`) in `app/globals.css`. `--destructive` was left at shadcn's default red.

**Components installed so far:** `button` only (from `init`). This phase's plan will need to install additional primitives via `npx shadcn@latest add form input card badge label` per RESEARCH.md's Standard Stack.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding (e.g. input icon to text) |
| sm | 8px | Compact element spacing (label to input, badge padding) |
| md | 16px | Default element spacing (form field vertical gap, card padding on mobile) |
| lg | 24px | Section padding (card padding on desktop, form group spacing) |
| xl | 32px | Layout gaps (space between login card and page edge on mobile) |
| 2xl | 48px | Major section breaks (space above/below the login card, "gerenciar equipe" header to table) |
| 3xl | 64px | Page-level spacing (vertical centering offset on login page) |

Exceptions:
- Icon-only buttons (e.g. "eye" toggle for password visibility) use a 44px touch target even though the icon itself is 16-20px — required for mobile tap accuracy, matches WCAG minimum.
- The login card has a fixed max-width of 400px (not a spacing token, but a layout constraint) to keep the form readable on desktop.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 500 (medium — closest available to the declared 2-weight cap; used only for form labels/table headers, not body text) | 1.5 |
| Heading | 20px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Notes:
- Exactly 4 sizes (16/14/20/28) and effectively 2 weights for prose (400 regular, 600 semibold); Label's 500 is shadcn's default `Label` component weight and is reserved exclusively for form labels and table column headers — never used for emphasis in running text (use 600 for that).
- Heading (20px/600) is the login card title ("Entrar") and section titles inside "gerenciar equipe" (e.g. "Convidar novo membro"). Display (28px/600) is reserved for the page-level "Gerenciar equipe" title only.
- Error/help text under form fields: 14px/400, not a separate role — uses Label's size at regular weight, in `--destructive` color for errors or `--muted-foreground` for help text.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` `oklch(1 0 0)` (white) / `oklch(0.145 0 0)` dark | Page background behind the login card and behind the "gerenciar equipe" content area |
| Secondary (30%) | `--card` `oklch(1 0 0)` on `oklch(0.97 0 0)` `--secondary` panels (light gray) / dark-mode equivalents | Login card surface, "gerenciar equipe" table container, page header bar |
| Accent (10%) | `--primary` `oklch(0.546 0.215 262.881)` (blue, light mode) / `oklch(0.623 0.188 259.815)` (blue, dark mode) | Reserved for: the "Entrar" button on login, the "Convidar" submit button in "gerenciar equipe", the active nav/role indicator, focus rings (`--ring`), and links ("Esqueci minha senha") |
| Destructive | `--destructive` `oklch(0.577 0.245 27.325)` (red, light mode) / `oklch(0.704 0.191 22.216)` (dark mode) | Reserved for: inline error messages ("Email ou senha inválidos"), invalid-field input borders, and any future destructive-action button (none exists in this phase's scope — see Copywriting Contract) |

Accent reserved for: the "Entrar" primary button, the "Convidar" primary button, the role badge/nav item indicating the logged-in user is a Supervisor (subtle, not a solid blue fill — outline or soft-blue badge per shadcn `Badge` "secondary" variant tinted blue), the "Esqueci minha senha" link, and focus-visible rings on inputs/buttons. Never used for entire section backgrounds, large blocks of body text, or more than one button per screen (only one primary action per screen — everything else is a secondary/outline/ghost button or a plain link).

## Screen-Specific Notes

### Login (`app/(auth)/login/page.tsx`)
- Single centered `Card` (max-width 400px), vertically centered on the page.
- Card header: "Entrar" (Heading, 20px/600).
- Fields (in order): Email (`Input type="email"`), Senha (`Input type="password"`, no visibility toggle required but acceptable at Claude's discretion during implementation).
- Below the fields, left- or right-aligned (Claude's discretion): "Esqueci minha senha?" link, styled as `--primary` blue text, no underline until hover/focus.
- Primary button "Entrar" spans the full card width, `--primary` fill.
- No signup link, no "criar conta" affordance anywhere on this screen — matches D-09.
- Inline error banner (not a toast) above the fields when login fails, using the Error state copy above, in `--destructive` text on a soft-red background (`Alert` pattern or plain text — Claude's discretion, but must be inline and persistent until the next submit attempt, not an auto-dismissing toast, since the user needs time to read it and retry).

### Forgot Password (`app/(auth)/forgot-password/page.tsx`)
- Same card layout/width as login for visual consistency.
- Single email field + "Enviar link de redefinição" primary button.
- On submit, replace the form with the Success feedback copy above (not a toast) — keeps the confirmation visible and matches the non-revealing security pattern.

### Reset Password (`app/auth/reset-password/page.tsx`)
- Same card layout. Single "nova senha" field (+ optional confirmation field, Claude's discretion) + "Salvar nova senha" primary button.

### Gerenciar Equipe (`app/(app)/equipe/page.tsx`, Supervisor-only)
- Page-level Display heading: "Gerenciar equipe" (28px/600), top of the content area, with the primary "Convidar" button aligned to its right (opens a form — inline section or `Dialog`, Claude's discretion, but must not navigate away from the list).
- Below the heading: a table/list of existing members showing nome, sobrenome, papel (as a `Badge` — neutral/secondary styling, not blue, to avoid overloading the one reserved accent color; blue is reserved for actionable elements only, not status labels), and email.
- Empty state (no members besides the logged-in Supervisor, or literally zero rows depending on whether the Supervisor's own row is shown): use the Empty state copy above, centered in the table area, with the "Convidar" action repeated/emphasized if the table itself is empty.
- Invite form fields (in order, per D-05/AUTH-02): nome, sobrenome, email, celular, papel (a `Select`/radio choosing Supervisor or Vendedor — explicit choice, no default pre-selected, per D-05).
- This screen must not be reachable (nav link, direct URL) by a Vendedor — enforced by the app layer redirecting non-Supervisors, backed by RLS as the real boundary (per RESEARCH.md's Anti-Patterns). Visually, a Vendedor never sees a broken/disabled version of this page — the route itself redirects.

### Role indicator (in the app's main layout/nav, visible on every authenticated page)
- Small, non-blue `Badge` (secondary/neutral variant) showing "Supervisor" or "Vendedor" next to the user's name — satisfies ROADMAP Phase 1 success criterion 3 ("o sistema reconhece se o usuário logado é Supervisor ou Vendedor e reflete esse papel na interface").
