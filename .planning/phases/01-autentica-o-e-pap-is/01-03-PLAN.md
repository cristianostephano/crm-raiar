<objective>
## Phase Goal (MVP user story)

**As a** sales-team member, **I want to** log in securely with my Supervisor or Vendedor role recognized system-wide, **so that** the database itself controls what I can see — starting at the data layer, not the screen.

## This plan

Deliver the walking skeleton's user-visible capability end-to-end: wire `@supabase/ssr` (browser client, server client, middleware session refresh), build the login screen (D-09 — email + senha + "Esqueci minha senha?" link, no sign-up affordance per D-01), and build the protected `app/(app)` area that redirects unauthenticated visitors and shows the logged-in user's name plus a neutral role `Badge` (AUTH-03 UI reflection; blue reserved for actions per UI-SPEC). A human then runs the full stack locally and confirms it works.

Purpose: This is the thinnest real slice that proves the whole stack — after this plan a real user can log in, see their role, and stay logged in across reloads (AUTH-01, AUTH-03 display, AUTH-04). Invite (plan 04) and password reset (plan 05) build on this.
Output: three `lib/supabase/*` clients, `middleware.ts`, the login page + form, the protected layout + landing page, and login + session-persistence tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> Next.js/Supabase Auth | Login credentials cross here; session lives in cookies |
| unauthenticated request -> protected (app) routes | The layout guard + middleware decide access |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07 | Spoofing | session validation in middleware/layout | high | mitigate | Server contexts call `auth.getUser()` (revalidated against Supabase), never `getSession()` (stale cookie trust) — RESEARCH Anti-Patterns / ASVS V3 |
| T-01-08 | Elevation of Privilege | role shown only in UI | medium | mitigate | The role badge is presentation only; authorization is enforced by RLS from plan 02, never by hiding UI (CLAUDE.md rule). The layout redirect is UX, not the boundary |
| T-01-09 | Information Disclosure | login error messaging | low | accept | Generic "e-mail ou senha incorretos" copy (UI-SPEC) does not reveal whether the email exists |
</threat_model>
