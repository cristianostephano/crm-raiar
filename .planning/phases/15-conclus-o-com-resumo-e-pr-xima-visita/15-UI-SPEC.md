# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase adds **one new shared dialog** (`components/agenda/ConcluirItemDialog.tsx`) and **modifies two existing surfaces**: `components/agenda/AgendaItemRow.tsx` (gains the "Concluir" action Phase 14 explicitly deferred) and `components/agenda/AgendaList.tsx` (owns the dialog's open/selected-item state, mirroring how it already owns `ClienteDetailSheet`'s state). There is **no new screen** — this is a write flow layered onto the existing `/agenda` screen from `14-UI-SPEC.md`. All tokens below are the project's **existing, already-shipped** design system (shadcn `base-nova` + Base UI + Tailwind v4 `@theme`); nothing new is introduced. Where a value was already locked by `13-UI-SPEC.md`/`14-UI-SPEC.md`, it is repeated here verbatim, not re-derived.

There is no `CONTEXT.md` (discuss-phase was skipped) and no phase-level `RESEARCH.md` for this phase — this contract is built directly from `ROADMAP.md`'s "Notas para o planejamento", `REQUIREMENTS.md` (CONC-01, VIS-03), the milestone-level research docs, and direct inspection of `GanhoFrequenciaDialog.tsx`/`PerdaMotivoDialog.tsx` (the structural precedent this phase's dialog must follow) and the existing `Popover`+`Calendar` single-date-picker pattern already used twice in `ClienteDetailSheet.tsx`. A few open UX questions had no upstream answer (exact resumo character bounds within the owner's "~280-500" note, exact validation copy, exact "nenhuma" presentation) — these are resolved below as explicit, documented defaults rather than left ambiguous, per this phase's instruction to decide rather than block.

### `ConcluirItemDialog.tsx` (new, ONE component parametrized by `origem: "prospeccao" \| "visita"` — per `ROADMAP.md`'s explicit instruction, not two dialogs)

| Element | Copy — `origem = "prospeccao"` | Copy — `origem = "visita"` |
|---------|-------------------------------|------------------------------|

| Resumo field label | `Resumo` (same for both origens) |

| Resumo helper text (idle, valid so far) | `Escreva 1-2 frases sobre o que aconteceu.` |
| Resumo character counter | `{length}/500 caracteres` (`text-xs text-muted-foreground`, right-aligned under the field) |
| Resumo validation — empty | `Escreva um resumo antes de concluir.` |
| Resumo validation — too short (1-9 chars) | `O resumo precisa ter pelo menos 10 caracteres.` |
| Resumo validation — too long (hard-capped by `maxLength`, server-side defense-in-depth only) | `O resumo pode ter no máximo 500 caracteres.` |
| Próxima visita field label | *(not rendered)* | `Próxima visita sugerida` |
| Próxima visita helper text | *(not rendered)* | `Confirme a data ou escolha outra.` |
| Próxima visita — "nenhuma" frequência notice (replaces the date field entirely) | *(not rendered)* | `Este cliente não tem frequência de visita definida — nenhuma próxima visita será agendada.` (`text-sm text-muted-foreground`, same slot the date field would otherwise occupy) |
| Submit error | `Não foi possível salvar as alterações. Tente novamente.` (reuse the exact `GENERIC_ERROR` string `GanhoFrequenciaDialog`/`PerdaMotivoDialog` already use — do not invent new copy) |
| Cancel button | `Cancelar` |
| Confirm button (idle) | `Concluir tarefa` | `Concluir visita` |
| Confirm button (submitting) | `Salvando...` (same for both origens) |
| Confirm button variant | `default` (primary) — **not** `destructive`, mirrors `GanhoFrequenciaDialog`'s precedent (completion is a positive outcome) |
| Confirm button disabled condition | disabled while submitting, or while the resumo is empty/under 10 characters — mirrors `PerdaMotivoDialog`'s `disabled={isSubmitting \|\| !valid}` pattern |

**Resumo length decision (documented default — flagged for confirmation):** `ROADMAP.md` records the owner's decision as "texto curto, ~280-500 caracteres, obrigatório" without pinning an exact number. This contract locks **min 10 / max 500 characters** as the concrete bounds: 500 is the upper bound of the owner's own stated range (favors "mínimo de fricção" — a vendor is never cut off mid-sentence), and 10 is the smallest threshold that blocks a trivial non-answer (`"ok"`, `"feito"`) without being annoying for a genuine short sentence. If the project owner specifies a different exact number later, only this file's numbers and `lib/validations/agenda.ts`'s `zod` schema change — no other contract element depends on the exact figures.

### No destructive action, no empty state, no new error-page copy is introduced by this phase

## Layout & Interaction Contract

*(Supplements the Copywriting Contract with the "where does this render, how does it behave" detail the checker/executor needs — same posture as `13-UI-SPEC.md`/`14-UI-SPEC.md`'s own Interaction Contract sections.)*

### `AgendaItemRow.tsx` (modified)

Adds a 4th content row inside `CardContent` (`flex flex-col gap-1.5`, same as the existing block), rendered **after** the date/responsável lines, right-aligned:

```
<div className="flex justify-end">
  <Button
    type="button"
    variant="outline"
    size="sm"
    onClick={(e) => { e.stopPropagation(); onConcluir() }}
  >
    <CheckCircle2 /> Concluir
  </Button>
</div>
```

`onClick` calls `e.stopPropagation()` before invoking the new `onConcluir` prop — identical defensive pattern to the existing `TooltipTrigger`'s `onClick={(event) => event.stopPropagation()}` a few lines above it in the same file, so clicking "Concluir" never also fires the row's own `onOpen` (which would open `ClienteDetailSheet` instead). `onConcluir` is a new required prop alongside the existing `onOpen`.

### `AgendaList.tsx` (modified)

Owns `ConcluirItemDialog`'s state exactly the way it already owns `ClienteDetailSheet`'s (`selectedClienteId`/`sheetOpen` pair) — add a sibling `concluirItem: AgendaItem | null` + `concluirDialogOpen: boolean` state pair. `AgendaItemRow`'s new `onConcluir` prop is wired to `() => handleOpenConcluir(item)`, mirroring `handleOpenCliente`. On the dialog's successful confirm, call the existing `handleRecarregar()` (bumps `reloadKey`) — the completed item disappears from the list, and (for `origem = "visita"` with a frequência ≠ "nenhuma") the newly-seeded next `visitas` row appears in whichever section its `data_prevista` sorts into, all from the same single re-fetch. No optimistic update / `@tanstack/react-query` is needed — this project has not installed that library (`SUMMARY.md`: "NOT installed") and the existing `AgendaList` fetch-on-mount + `reloadKey` pattern already covers this correctly.

### `ConcluirItemDialog.tsx` (new — structural mirror of `GanhoFrequenciaDialog.tsx`)

Props:
```
open: boolean
onOpenChange: (open: boolean) => void
origem: "prospeccao" | "visita"
razaoSocial: string
itemTitulo: string
frequenciaVisita: FrequenciaVisita | null   // only meaningful when origem === "visita"
onConfirm: (resumo: string, proximaData: string | null) =>
  Promise<{ error?: { message: string } } | undefined>
```

1. **Resumo field:** a single `Textarea` (`components/ui/textarea.tsx`, already installed), `maxLength={500}`, controlled state, `flex flex-col gap-1.5` label+control block (same rhythm as the sibling dialogs' one required field). Character counter renders directly under the field. Validation runs on submit (matching `PerdaMotivoDialog`'s defense-in-depth pattern — the Confirm button is already `disabled` for the same condition, so this only guards a stray Enter-key submit inside the textarea, which does not submit forms by default but is guarded anyway per the existing precedent's own reasoning).
2. **Próxima visita field (`origem === "visita"` only):**
   - If `frequenciaVisita` is `null`/`"nenhuma"`: render only the "nenhuma frequência" notice text (Copywriting Contract above) — no date field, no `Popover`, no `Calendar`. This is success criterion 4's literal requirement ("conclui a visita normalmente e nenhuma próxima visita é criada") — the UI must make it visually obvious *before* submit that no next visit will be scheduled, not just silently omit the field.
   - Otherwise: pre-fill a suggested date the moment the dialog opens, computed **client-side, off `new Date()` (today's real local date — never a parsed string)**, using `date-fns`: `addWeeks(new Date(), 1)` for `semanal`, `addWeeks(new Date(), 2)` for `quinzenal`, `addMonths(new Date(), 1)` for `mensal` (`date-fns`'s `addMonths` clamps correctly at month-end, matching Pitfall 1's exact requirement). Render it in the **identical `Popover`+`Calendar` single-date-picker composition already used twice in `ClienteDetailSheet.tsx`**: `PopoverTrigger` styled `w-fit rounded-lg border border-input px-2.5 py-1.5 text-left text-sm` showing `format(selectedDate, "dd/MM/yyyy")`, `PopoverContent className="w-auto p-0"` containing `<Calendar mode="single" selected={selectedDate} onSelect={setSelectedDate} />` (no `numberOfMonths` override — a single month is enough for a nearby suggested date, unlike `PeriodoFilter`'s 2-month range picker). This is purely a **display-time preview** (Architecture Pattern 1, point 1) — it never calls the RPC and never does string-date arithmetic, so Pitfall 1 does not apply to this client-side computation.
   - Whatever date is selected when "Concluir visita" is pressed (the pre-fill, untouched, or a manually adjusted one) is passed as `onConfirm`'s `proximaData` argument, formatted `yyyy-MM-dd` (plain date string, matching `visitas.data_prevista`'s plain-`date` column type — never `toISOString()`, which reintroduces the UTC-midnight bug this project's own Pitfall 1 already documents).
3. **`origem === "prospeccao"`:** only the resumo field renders — no próxima-data section at all, regardless of the cliente's `frequenciaVisita` (that value has no meaning for a prospecção task). `onConfirm` is called with `proximaData = null` unconditionally in this branch.
4. **Reset on close:** mirrors `GanhoFrequenciaDialog`'s `handleOpenChange` — clears resumo, selected date, and error states whenever the dialog closes (via `onOpenChange`, not a synchronous effect on `open` flipping false).
5. **Loading state:** none needed — unlike `PerdaMotivoDialog` (which loads `motivos` from the DB), this dialog has no async data to fetch on open; the frequência value and item metadata are already loaded with the Agenda list itself and passed in as props.

### What this phase does NOT render

No per-client diary view (Phase 16), no ATV-01/ATV-02 fields, no planilha/import flow (Phase 17). This phase's entire new UI surface is: the row-level "Concluir" button, and `ConcluirItemDialog` itself.
