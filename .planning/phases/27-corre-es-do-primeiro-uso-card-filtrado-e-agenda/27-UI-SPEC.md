## Phase-Specific Contract Detail

### KAN-03 — "identical rendering regardless of filter state"

The design source of truth is `components/clientes/ClienteCard.tsx`'s CURRENT unfiltered rendering — there is no new design to specify. The contract is behavioral, not visual-token-based, precisely because RESEARCH.md confirms the code-level root cause is still unknown:

1. **Same fields, same order:** categoria `Badge` (outline variant) → optional overdue `TriangleAlert` → vendedor name (`showResponsavel && responsavelNome`) → cidade/estado line (`rotuloCidadeEstado`) → quick-action row (phone, WhatsApp, schedule) → `EtapaArrowButton` pair (back/forward), in that exact order, whether or not a vendor filter is active.
2. **Same card width:** `w-[280px] shrink-0` (confirmed byte-identical in both the `dragDisabled` and `DndContext` branches of `KanbanBoard.tsx` today) must remain the width in both filtered and unfiltered states.
3. **Same truncation behavior:** `truncate` on the title (`CardTitle`) and on the vendedor line (`<p className="truncate ...">`) — text must ellipsis the same way under filter as without; no name should visually "cut" differently (KAN-03 success criterion 2).
4. **Same touch targets:** all quick-action icons and the two arrow buttons stay `size-11` (44px) with the same `hover:bg-muted hover:text-foreground` states, functioning identically (KAN-03 success criterion 3 — explicit regression guard against the `260921-n0a` quick task that added the arrows).
5. **What must NOT happen:** no new CSS class, breakpoint, or conditional render path introduced "to fix" filtered mode — since RESEARCH.md's two independent static-analysis passes found no code-level cause, any planned code change must be justified by the mandatory live-diagnosis checkpoint's findings (see RESEARCH.md's diagnostic script), not guessed. If the diagnosis finds no reproducible difference at all on the current `staging` deploy, that itself is a valid outcome to report back — not a license to invent a defensive fix nobody asked for.

This section is intentionally a CONTRACT ("must render identically") rather than a CSS/prop prescription — per the phase framing, prescribing a specific fix ahead of the live diagnosis would contradict RESEARCH.md's own recommendation.

### AGD-15 — "match nomeExibicaoCliente() exactly, nothing else changes"

1. Swap `AgendaSemDiaFixo.tsx`'s `CardTitle` (`title` attribute AND children — both call sites) from raw `{cliente.razaoSocial}` to `nomeExibicaoCliente(cliente.razaoSocial, cliente.nomeFantasia)`, matching `ClienteCard.tsx`'s existing dual-call-site pattern exactly (see RESEARCH.md Pattern 1 / Code Examples).
2. No new className, no new layout — the existing `"truncate text-base leading-tight font-semibold"` stays untouched; only the computed string changes.
3. `responsavelNome` line stays exactly as-is (D-03) — it must appear alongside, never instead of, the corrected client name.
4. Upstream 3-point data-plumbing change (RESEARCH.md Pattern 2) is a prerequisite, not a visual decision: `getClientesSemDiaFixo()`'s `select()` + `ClienteSemDiaFixoRow` + `mapClienteSemDiaFixoRow()` + `ClienteSemDiaFixo` type all need `nome_fantasia`/`nomeFantasia` added before the component can call `nomeExibicaoCliente()` — flagged here for the planner/executor, not a UI contract concern per se.
