# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase adds **one new screen** (`/agenda`) and **one modified surface** (`AppSidebar.tsx`, new top nav item). It is a **read-only** phase — `agenda_do_vendedor()` is a pure `SELECT` RPC (see `ARCHITECTURE.md` Pattern 2); there is no "Concluir" action, no form, no write flow anywhere in this phase's UI. The completion flow (resumo + próxima data) belongs to Phase 15 and is explicitly out of scope here. All tokens below are the project's **existing, already-shipped** design system (shadcn `base-nova` + Base UI + Tailwind v4 `@theme`) — nothing new is introduced. Where a value was already locked by `13-UI-SPEC.md` (spacing/typography/color), it is repeated here verbatim, not re-derived.

## Spacing Scale

Declared values (existing project tokens — same scale locked in `13-UI-SPEC.md`, reused verbatim):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`gap-1`) | Icon-to-text gaps inside a badge/tooltip trigger |
| sm | 8px (`gap-2`) | Compact row-internal spacing (badge + title, date + icon) |
| md | 16px (`gap-4`, `px-4`, `py-4`) | Default spacing between an item row's internal blocks, page toolbar padding |
| lg | 24px (`py-6`, `gap-6`) | Spacing between agenda sections ("Atrasado" / "Hoje" / "Próximos dias"), loading/error full-width messages |
| xl+ | not used this phase | No new layout-level spacing introduced |

Exceptions: **`gap-1.5` (6px)** — reused for section-header-to-list-body rhythm (matches the established `flex flex-col gap-1.5` label+control pairing convention). **`gap-2` between item rows within a section** (matches `HistoricoTimeline`'s `flex flex-col gap-2` list rhythm) — do not introduce a different inter-row gap.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | default (~1.43, Tailwind `text-sm` default) |
| Label / section header | 14px (`text-xs` for section headers specifically, see below) | 600 (semibold) | 1 (`leading-none`) |
| Item title (cliente razão social) | 16px (`text-base`) | 600 (`font-semibold`) | default — matches `ClienteCard`'s `CardTitle` exactly |
| Heading | 20px (`text-xl`) | 600 (`font-semibold`) | default (~1.4) — used for the page title "Agenda" |
| Display | not used this phase | — | — |

**Section headers** ("Atrasado (3)", "Hoje (2)", "Próximos dias (5)") use `text-xs font-semibold tracking-wide text-muted-foreground uppercase` — this is a 12px size, the one deliberate addition to the 3-size scale already locked in `13-UI-SPEC.md` (14/16/20). It mirrors `AppSidebar.tsx`'s own section-label treatment (`text-xs font-medium tracking-wide uppercase`), adapted from `text-slate-500` (dark sidebar) to `text-muted-foreground` (light page body) — same role, different surface. Total distinct sizes this phase: **12, 14, 16, 20** — within the 3-4 size budget the design-contract rule allows.

Do not introduce a 5th size or a 3rd weight anywhere in this phase.

## Layout & Interaction Contract

*(Supplements the Copywriting Contract with the "where does this render, how does it behave" detail the checker/executor needs — same posture as `13-UI-SPEC.md`'s own Interaction Contract section.)*

### Page structure — `app/agenda/page.tsx` (new)

1. Server Component page shell (route group `(app)`, same layout wrapper as `/clientes`/`/dashboard`) renders a Client Component `AgendaList` that owns its own fetch/loading/error state, mirroring `ComparativoVendedorTable`'s fetch-on-mount posture exactly (`useState<FetchState>`, `useEffect` calling a Server Action that wraps `supabase.rpc('agenda_do_vendedor')`, `cancelled` guard, `reloadKey` retry counter).
2. Page header: `Agenda` (`text-xl font-semibold`) + subtitle (`text-sm text-muted-foreground`) on the left; the Vendedor `Select` filter (Supervisor only) on the right, same header row pattern the Dashboard already uses for its `PeriodoFilter`.
3. Below the header: three sections in fixed order — **Atrasado, Hoje, Próximos dias**. A section is omitted entirely (no header, no empty placeholder) when it has zero items — only the whole-list empty state (below) renders when all three are empty.
4. Each section is a `flex flex-col gap-2` list of item rows, preceded by its `text-xs font-semibold tracking-wide text-muted-foreground uppercase` header showing the live count, e.g. `Atrasado (3)`.

### Item row — new `components/agenda/AgendaItemRow.tsx`

Each row is a `Card` (`size="sm"`, same primitive `ClienteCard` already uses), `role="button"`/`tabIndex={0}`/`onKeyDown` Enter-or-Space pattern copied verbatim from `ClienteCard.tsx`, opening the existing `ClienteDetailSheet` via the same `clienteId`-driven controlled-sheet pattern `KanbanBoard.tsx` already implements (`selectedClienteId` state + `handleOpenCliente`).

Left-border rule (success criterion 3 — exact kanban precedent reuse):
- Rows inside the **Atrasado** section: `border-l-4 border-l-red-500` (the identical utility `TASK_STATUS_BORDER.none` already uses).
- Rows inside **Hoje** / **Próximos dias**: no colored left border — plain `Card` default border only.

Row content (`flex flex-col gap-1.5` internal, `px-3 py-2.5` per the compact `Card size="sm"` convention already established):
- Line 1: cliente `razaoSocial` (`text-base font-semibold`, `truncate`) + origem `Badge` inline to its right.
  - Origem = `prospeccao` → `<Badge variant="outline"><ClipboardCheck /> Prospecção</Badge>`
  - Origem = `visita` → `<Badge variant="secondary"><Repeat /> Visita</Badge>`
  - (Icon choice is Claude's discretion within `lucide-react`; `ClipboardCheck`/`Repeat` were picked for semantic fit — one-off task vs. recurring cadence — and neither collides with an icon meaning already established elsewhere in this codebase.)
- Line 2: item título — the `tipos_tarefa` name for `origem = prospeccao` (e.g. "Visitar", "Mandar mensagem" — the existing Supervisor-editable vocabulary), or the literal string `Visita` for `origem = visita` (matches `agenda_do_vendedor()`'s own `'Visita'` literal per `ARCHITECTURE.md`'s example RPC body) — rendered `text-sm text-muted-foreground`.
- Line 3: date row — formatted `dd/MM` (`date-fns` `format(parseISO(item.data), "dd/MM")`, **never** `new Date(item.data)` — Pitfall 1 applies to display too) in `text-sm text-muted-foreground`. Rows inside **Atrasado** additionally show the `TriangleAlert` icon (`size-3.5 text-amber-500`, exact classes from `ClienteCard.tsx`) with a `Tooltip`/`TooltipContent` reading `Atrasado desde {dd/MM}.`, positioned inline after the date — copy the `Tooltip`/`TooltipTrigger` composition from `ClienteCard.tsx` verbatim (including `onClick={(e) => e.stopPropagation()}` so the tooltip never triggers the row's own open-sheet handler).
- Line 4 (Supervisor view only, or when the Vendedor filter is set to "Todos os vendedores"): `responsavelNome`, `text-sm text-muted-foreground`, `truncate` — same `showResponsavel` gating concept `ClienteCard` already uses.

### Sidebar — `AppSidebar.tsx` (modified)

1. `PRINCIPAL_SECTION.links` gains a new first entry: `{ href: "/agenda", label: "Agenda", icon: ListChecks }` — inserted **before** the existing `Clientes` entry (AGD-02's literal ordering requirement). Final order: `Agenda, Clientes, Dashboard`.
2. `ListChecks` (Claude's discretion, `lucide-react`) — distinct from `Users` (Clientes) and `LayoutDashboard` (Dashboard), already unused elsewhere in this file.
3. Count badge (expanded, `!compact`): render the link content as `flex items-center justify-between` (instead of the current single-line `flex items-center gap-3`) — icon+label on the left, a small `Badge` (`variant="default"`, i.e. `bg-primary text-primary-foreground`, sized down to match the sidebar's compact rhythm: `h-4 min-w-4 px-1 text-[10px]`) on the right showing `{count}`, omitted entirely when `count === 0`. This is the one nav item whose `NavLink` needs a dynamic badge — model it as an optional `badgeCount?: number` on the `NavLink` type (or a small dedicated branch just for the Agenda entry, since it's the only nav item with dynamic content) rather than changing every other static link.
4. Count badge (compact/collapsed rail): a small circular indicator overlaid on the icon, reusing the exact positioning convention `FiltersPopover.tsx`'s "active filters" dot already established (`absolute -top-1 -right-1 ... rounded-full bg-primary`), sized up slightly to fit 1-2 digits (`size-3.5` circle, `text-[9px] text-primary-foreground leading-none flex items-center justify-center`, capped display at `9+` for double-digit counts to avoid the rail overflowing). Omitted entirely when `count === 0`.
5. The `Tooltip`/`TooltipContent` already wrapping every compact-mode link gets the count folded into its text per the Copywriting Contract above (`Agenda (5)` vs. plain `Agenda`).
6. Count is fetched once per page load (Server Component reading `agenda_do_vendedor()`'s row count, or a lightweight dedicated count query — planner's choice) and passed down through the existing `AppSidebar` props chain; it does not need to be live/real-time for this milestone (no Realtime subscription — matches `STACK.md`'s "keep it optional/deferred for MVP" guidance).

### Vendedor filter (Supervisor only, AGD-05)

Reuses `FiltersPopover.tsx`'s exact `Select` + `SEM_FILTRO` sentinel pattern for the Vendedor dimension (`components/clientes/FiltersPopover.tsx` lines ~217-244), but rendered **standalone** on the Agenda page toolbar (not inside a `Popover`) — Agenda has exactly one filter dimension, so a popover wrapper would be unnecessary chrome for a single control. Options list: same `vendedorOptions: { id: string; nome: string }[]` shape already used elsewhere, sourced from the RLS-scoped rows returned by the agenda query itself (every distinct `responsavel` present) rather than a separate lookup call. Applying the filter re-scopes the three sections' counts and rows client-side (the full team's agenda is already loaded in one round trip for Supervisor; filtering by vendedor is a pure client-side narrow, not a new query — same "filter locally over an already-fetched RLS-scoped set" precedent `FiltersPopover`/`clienteAtendeFiltros` already establish for the Clientes screen).

### What this phase does NOT render

No "Concluir" button, no resumo field, no next-date suggestion/confirmation UI, no per-client diary — all four belong to Phase 15 (conclusion flow) and Phase 16 (diary), per `ROADMAP.md`'s explicit phase boundaries. Do not scope-creep either into this phase's UI.
