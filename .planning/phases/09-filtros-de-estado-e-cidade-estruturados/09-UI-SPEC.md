# Phase 9 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase converts two existing free-text fields (Estado, Cidade) into structured pickers, applied consistently across four touchpoints: cadastro (`ClienteQuickCreateForm.tsx`), edição (`ClienteDetailSheet.tsx`), filtro (`FiltersPopover.tsx`), and importação (`lib/importacao/annotarLinha.ts`'s validation copy, surfaced by Phase 6's existing `ImportPreviewTable`). No new screen, no new type scale, no new color is introduced — every token below is reused exactly from the tokens already established and approved in Phase 8's UI-SPEC (`.planning/phases/08-rolagem-por-coluna-no-kanban/08-UI-SPEC.md`). The only genuinely new visual element is the Cidade `Combobox` itself (a shadcn `base-nova`/Base UI file copy, not a custom-built control) and its disabled/search/empty states, specified precisely under "Component-Specific Implementation Notes."

## Component-Specific Implementation Notes

*(Extends the template — this phase's contract lives mostly here, since it governs the exact behavior of a cascading two-field pattern reused across 4 touchpoints rather than introducing a new visual surface. Per `RESEARCH.md`'s Recommended Project Structure, the Estado+Cidade cascade wiring should live in one shared `EstadoCidadeFields.tsx` component consumed by both `ClienteQuickCreateForm.tsx` and `ClienteDetailSheet.tsx` — but the contract below applies regardless of exactly how the planner splits components, since `FiltersPopover.tsx` needs the same cascade behavior with its own draft-state wiring, not the shared component.)*

### 1. Estado field — `<Select>` over the fixed `UFS` constant (all 3 form/filter touchpoints)

- Reuse `components/ui/select.tsx` exactly as already used for "Responsável"/"Categoria" elsewhere in these same forms — same `SelectTrigger`/`SelectContent`/`SelectItem` classes, same `h-8`/`text-sm`/`rounded-lg border-input` trigger.
- Options: the 27 UFs from `lib/clientes/ufs.ts`'s `UFS` constant, rendered in the array's existing order (alphabetical by sigla — do not re-sort, do not group by region).
- Cadastro/edição forms: no "nenhum" sentinel — Estado is a required field (`z.enum(UFS)`), matching the existing required-field convention for "Responsável".
- `FiltersPopover.tsx`: keep the existing `SEM_FILTRO` sentinel pattern ("Todos os estados" as the first `SelectItem`, value `__todos__`) — Estado stays optional in the filter context, this is the one touchpoint where "no filter" must remain selectable.
- Selecting a new Estado **must reset the Cidade value to empty** in every touchpoint (cadastro, edição, filtro) — carrying over a previously-picked city name into a newly-selected state is the exact bug class D-02's cascade gating exists to prevent.

### 2. Cidade field — `Combobox` over `cidades_por_estado(uf)` (all 3 form/filter touchpoints)

**Visual parity with `Select`:** the Combobox trigger must look identical in size/border/radius/type to the `SelectTrigger` it replaces — `h-8`, `text-sm`, `rounded-lg border border-input bg-transparent`, same `disabled:opacity-50 disabled:cursor-not-allowed` treatment, same trailing chevron icon size (`size-4`, `text-muted-foreground`). A user should not be able to tell "this one is a Combobox and that one is a Select" from size/border alone — only from the presence of a type-to-search affordance once opened.

**Disabled state (D-02):**
- `disabled` whenever no Estado is selected yet (`!estado`).
- Placeholder text while disabled: **"Escolha o Estado primeiro"** (see Copywriting Contract) — rendered via the trigger's own placeholder slot, not a separate line of helper text, so it disappears automatically the instant the field becomes enabled (no leftover helper text to manually clear).
- The moment Estado changes to a real value, the Combobox becomes enabled and its placeholder switches to "Selecione a cidade" (forms) / "Todas as cidades" (filtro) with an empty selection — per §1, any prior Cidade value is cleared, never silently kept.

**Enabled/open state (search behavior):**
- Typing filters the list to municipalities of the selected UF whose name matches the typed substring, case-insensitive and diacritic-insensitive (e.g. typing "sao" must match "São Paulo") — this is Base UI `Combobox`'s built-in filtering behavior; do not hand-roll a separate filter function per Pitfall guidance in `RESEARCH.md`'s "Don't Hand-Roll" table.
- Keyboard: Arrow Up/Down moves the highlighted item, Enter selects the highlighted item and closes the popup, Escape closes the popup without changing the current selection — standard Base UI `Combobox` behavior, no custom key handling needed.
- Popup list container: same visual chrome as `SelectContent` (`bg-popover`, `rounded-lg`, `shadow-md`, `ring-1 ring-foreground/10`), scrollable when the filtered result set exceeds the popup's `max-h-(--available-height)` (same anchor-relative max-height Base UI already computes for `Select`) — never render all ~645 São Paulo cities unscrolled.
- Empty-search-result row: "Nenhuma cidade encontrada" (see Copywriting Contract), 14px/regular/`text-muted-foreground`, no icon — matches `FiltersPopover`'s existing plain-text empty-state precedent (its "Nenhum produto cadastrado ainda." row).
- Selected-item indicator inside the list: reuse the existing `CheckIcon` pattern from `SelectItem`/`SelectPrimitive.ItemIndicator` — same size (`size-4`), same position (`absolute right-2`).

**Data source:** every one of the 3 UI touchpoints calls the same `cidades_por_estado(p_uf)` RPC directly from the browser Supabase client (read-open RLS, no Server Action indirection) — never re-implemented per-component, per `RESEARCH.md`'s "Don't Hand-Roll" table.

### 3. Cadastro (`ClienteQuickCreateForm.tsx`) and Edição (`ClienteDetailSheet.tsx`)

- Estado and Cidade **stay inside the existing `grid grid-cols-3 gap-3` row** they already occupy (currently: Complemento / Cidade / Estado, in that column order) — this phase does not change the row's layout, column count, or column order within the row; it only replaces the two `<Input>`s with the `<Select>`/`Combobox` pair from §1/§2.
- Each field keeps its existing `FormItem`/`FormLabel`/`FormControl`/`FormMessage` wrapper (`grid gap-2`, 8px) exactly as every other field in these two forms — no bespoke spacing introduced for these two fields specifically.
- Cidade's `FormControl` wraps the `Combobox` the same way it currently wraps the `<Input>` — `React.cloneElement`-based prop injection (`id`, `aria-describedby`, `aria-invalid`) must keep working, since `FormControl` (this project's hand-rolled Radix-`Slot` substitute, `components/ui/form.tsx`) expects exactly one cloneable child element.

### 4. Filtro (`FiltersPopover.tsx`) — reorder + cascade + exact-match fix (LOC-03, D-02, Pitfall 3/4)

- **Field order (LOC-03):** Estado's `<Select>` must render immediately above Cidade's `Combobox` in the JSX (and therefore in on-screen/tab order) — the current implementation has this backwards (Cidade `<Input>` first, ~line 255-265; Estado `<Select>` second, ~line 267-290). Swap the two blocks.
- **Cascade gating applies here too:** Cidade's `Combobox` in the filter popover is `disabled` until `draft.estado` has a value, exactly like §2 — this is the one touchpoint where a user might reasonably expect to filter by Cidade alone without picking Estado first, but D-02's decision (low-risk, evaluated project-wide by Claude's discretion) applies uniformly across all 4 touchpoints, not just the forms. Placeholder while disabled: "Escolha o Estado primeiro" (same copy as §2).
- **`estadoOptions` prop is now dead:** `FiltersPopover`'s `estadoOptions: string[]` prop (today derived from `KanbanBoard.tsx`'s in-memory `estadoOptions` `useMemo`) is replaced by importing the fixed `UFS` constant directly inside `FiltersPopover.tsx` — do not keep threading a now-unused prop through `KanbanBoard.tsx`. Remove the `estadoOptions` prop and its `useMemo` in the same change.
- **Exact-match fix (Pitfall 4):** `clienteAtendeFiltros`'s Cidade branch (`FiltersPopover.tsx:85-88`) changes from substring match (`cliente.cidade.toLowerCase().includes(cidadeFiltro)`) to an exact, case-insensitive equality check (`cliente.cidade.toLowerCase() === cidadeFiltro`) — Cidade is now a value picked from a fixed list, so substring matching is no longer the correct semantic (and would produce false-positive matches, e.g. a city name that's a substring of another). `filtros.cidade`'s type stays a plain `string` (not `string | null`) per the existing `ClienteFiltros` shape — an empty string still means "no filter applied" for this dimension, unchanged.
- **`contarFiltrosAtivos`** already counts Cidade via `filtros.cidade.trim() !== ""` — no change needed there, an exact-match Combobox selection still populates `draft.cidade` as a plain string.

### 5. Legacy/inconsistent Estado values (LOC-04, D-01) — no new UI needed

- Per D-01 and this phase's own discretion note: a cliente record whose stored `estado` doesn't match any of the 27 UFs after the simple case/whitespace-insensitive backfill is **not** specially flagged, blocked, or given a warning banner in the UI. It simply displays/edits normally — when the `<Select>` in `ClienteDetailSheet.tsx` mounts with a stale, out-of-list `estado` value, standard `Select` behavior applies (the value renders via `SelectValue`'s items lookup if present in `items`, or falls back silently otherwise); the user picks a valid UF from the list the next time they open/save that record, which naturally corrects it. No custom "invalid legacy value" UI treatment is in scope for this phase.

### 6. Importação (`lib/importacao/annotarLinha.ts` validation surfaced by Phase 6's existing preview UI)

- No new screen or component — Phase 6's `ImportPreviewTable` already has a per-row error/reason column; this phase only changes what `annotarLinha.ts` writes into that existing column's string list for a bad Estado/Cidade cell (see Copywriting Contract's exact strings). No visual change to `ImportPreviewTable` itself.
- The spreadsheet column-mapping step (choosing which spreadsheet column maps to "Estado"/"Cidade") is unchanged visually — same mapping UI as today, only the downstream per-row validation logic against those two columns changes.
