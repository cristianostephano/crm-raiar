## Phase-Specific Contract Detail

### 1. Menu icon for "Encerrados" (NEW decision — resolves RESEARCH.md's Assumptions Log A1 / LOW-confidence flag)

- **Icon:** `PauseCircle` (`lucide-react`). **Verified against the installed version (`1.24.0`)** by inspecting `node_modules/lucide-react` directly: `PauseCircle` is a live, currently-exported alias of the canonical `CirclePause` icon — it is not a name that has been removed or renamed away in this version. Confidence upgraded from RESEARCH.md's LOW to HIGH.
- **Collision check:** `components/layout/AppSidebar.tsx` currently imports `Archive, BadgeCheck, ChevronLeft, ChevronRight, FileUp, LayoutDashboard, ListChecks, LogOut, Settings, Users, UsersRound`. `PauseCircle` collides with none of these, and its "pause"/"stopped" semantics reads distinctly from `Archive` (Perdidos — "filed away") — a client that is encerrado is not permanently filed, it's paused, so the icon choice is also semantically correct, not just non-colliding.
- **Placement in `PRINCIPAL_SECTION`:** immediately after `{ href: "/perdidos", label: "Perdidos", icon: Archive }`, before `{ href: "/dashboard", ... }` — same nav level as Agenda/Clientes/Perdidos/Dashboard (never nested under Clientes), same "no badge, ever" rule as Perdidos.
- **Alternative if a future lucide-react major removes the `PauseCircle` alias:** `CircleOff` (also confirmed present in this install) is the next-best fallback already vetted in `node_modules` — flagged here so the executor doesn't need to re-verify from scratch if this ever needs revisiting.

### 2. Status Select entry point (NEW decision — resolves "hidden vs disabled")

- **Convention:** mirror the existing "Ganho" disabled-with-tooltip pattern in `ClienteDetailSheet.tsx` **exactly** — do not invent a new hidden/conditional-rendering pattern. The "Encerrado" `SelectItem` is **always present** in the list (never conditionally omitted), and its `disabled` prop follows the same shape as the existing "Ganho" option:

  ```tsx
  // Existing precedent (ClienteDetailSheet.tsx, ~line 1120-1126):
  <SelectItem
    key={option.value}
    value={option.value}
    disabled={
      option.value === "ganho" && cliente.etapa !== ETAPA_FINAL
    }
  >

  // New "encerrado" option, same shape, same file, condition swapped to
  // status-based (per D-04: reachable only from "ganho", not etapa-based —
  // the DB-side backstop CHECK mirrors chk_ganho_somente_etapa_final via
  // etapa, but the UI-reachability condition the Select actually needs to
  // read is the CURRENT status, exactly as "ganho"'s own disabled check
  // reads the current etapa):
  <SelectItem
    key={option.value}
    value={option.value}
    disabled={
      option.value === "encerrado" &&
      cliente.statusAcompanhamento !== "ganho"
    }
  >
  ```
- **Tooltip:** same `Info` icon + `Tooltip`/`TooltipTrigger`/`TooltipContent` composition already used for "Ganho" (verbatim reuse of the `GANHO_TOOLTIP`-style constant pattern), new constant `ENCERRADO_TOOLTIP = 'Disponível somente quando o cliente já está "Ganho".'` — same `pointer-events-auto` / `stopPropagation` wiring so the tooltip doesn't trigger the Select's own click-to-open behavior.
- **Status dot color (visual parity with the existing `em_andamento`/`perdido`/`ganho` colored dots in the same Select):** a 4th color is needed — do not reuse `bg-destructive` (already used for `perdido`, and Encerrado is not a "loss" in the funnel-metrics sense per ENCR-05's success criterion 5) and do not reuse `bg-green-600` (already used for `ganho`, and the two must stay visually distinguishable at a glance in the same dropdown). Use `bg-slate-500` (a neutral mid-gray) — reads as "paused/inactive," distinct from both the destructive-red of "perdido" and the success-green of "ganho," and doesn't introduce a genuinely new hue to the palette (Tailwind's slate scale is already in active use in `AppSidebar.tsx`'s `bg-slate-900`/`text-slate-300`/etc., so this is a reuse of an already-approved neutral, not a new color decision requiring its own accent-budget justification).
- **Selecting "Encerrado":** opens `EncerramentoMotivoDialog` — same interaction shape as `handleStatusSelect`'s existing `perdido`/`ganho` branches (a new `if (novoStatus === "encerrado") { setEncerramentoDialogOpen(true); return }` branch, mirroring the existing two branches verbatim).

### 4. Reactivation edge-case error copy (NEW — resolves RESEARCH.md's Open Question 1)

- **Trigger:** vendedor taps "Reativar" on a client whose `frequencia_visita` was never set (legacy pre-Phase-13 grandfathered client, VIS-04) — `marcarStatus`'s effective-frequency fallback (RESEARCH.md Pattern 2 / Pitfall 1) has no stored value to fall back to.
- **Mechanism:** same transient-banner mechanism already used by `KanbanBoard.tsx` for failed mutations and by `PerdidosList.tsx`'s equivalent failed-Reabrir path — **not** a new dialog, **not** a blocking modal, and it must **not** silently break D-09's "no confirmation dialog" rule by popping open `GanhoFrequenciaDialog` as a surprise second step. The row stays in place (no optimistic removal, same convention as Phase 28), and the banner surfaces inline.
- **Exact copy:** "Este cliente nunca teve uma frequência de visita definida. Abra a ficha dele para definir uma frequência antes de reativar."
- **Tone check:** this is the one error message on this screen naming a concrete next step (open the ficha) rather than a generic retry, because retrying the same tap will fail identically every time — an undifferentiated "Tente novamente" here would be actively misleading (RESEARCH.md's own framing of this as "an actionable error, not a silent break of the no-confirmation rule").
