<objective>
Levar a exigência de CNPJ até a tela, reusando o caminho de ganho que já existe: o mesmo diálogo, a mesma Server Action, a mesma chamada de RPC. O diálogo `GanhoFrequenciaDialog` ganha um campo CNPJ ao lado da frequência de visita; `marcarStatus` ganha um parâmetro a mais e o repassa como `p_cnpj`; a ficha do cliente sincroniza o valor recém-informado para não apagá-lo no salvamento seguinte.

E é aqui que o grandfathering do CNPJ-02 aparece para o usuário: a tela precisa exigir o CNPJ exatamente quando o banco exige — na transição para ganho — e ficar em silêncio para quem já é ganho, sem cobrança, sem badge, sem modal.

Output: o fluxo de ganho funcionando de ponta a ponta com CNPJ, e os testes de componente provando as duas metades da regra.

## Contrato herdado do plano 18-01 (já aplicado no banco)

```
mover_card_funil(
  p_cliente_id       uuid,
  p_nova_etapa       etapa_funil,
  p_novo_status      status_acompanhamento_enum default null,

```

Regra do guard, palavra por palavra, para que a tela e a Server Action digam a mesma coisa:
levanta exceção quando `p_novo_status = 'ganho'` **E** a linha é visível ao chamador **E**
`status_acompanhamento` atual do cliente **não** é `'ganho'` **E** o CNPJ efetivo
(`p_cnpj` aparado, ou o `clientes.cnpj` já gravado, aparado) é vazio.

Consequências que este plano precisa respeitar:
- Cliente que já é ganho → o RPC não exige CNPJ. A tela também não pode exigir.
- Cliente que já tem `clientes.cnpj` gravado → o RPC não exige `p_cnpj`. A tela pode pré-preencher e seguir.
- Espaço em branco não conta como preenchido (o banco apara antes de checar). A tela deve aparar também, para não oferecer um botão habilitado que o banco vai recusar.
- Nenhuma validação de formato existe no banco. Nenhuma deve ser inventada aqui.
