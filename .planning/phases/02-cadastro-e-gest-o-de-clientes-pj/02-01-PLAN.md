<objective>
Create the entire Phase 2 data model in one migration (`0002_clientes_and_funil.sql`) — the `clientes` table (which IS the funnel card, per the 1:1 modeling decision below), the four editable-list lookup tables (seeded), the `cliente_produtos` join, `tarefas`, `historico`, the `mover_card_funil` RPC, the auto-history + stage-timestamp triggers, and every table's RLS policy and business-rule CHECK constraint — then push it live and prove the authorization and business rules hold against direct API calls.

**Data-model decision (the open modeling question, resolved):** a `clientes` row **is** the funnel card — `etapa`, `status_acompanhamento`, `motivo_perda_id`, `observacao`, and card ordering live as columns directly on `clientes` (1:1 model). This follows `.planning/research/ARCHITECTURE.md` ("a `clientes` row *is* the funnel card ... there is no separate opportunity/deal entity in the MVP") and CLAUDE.md's domain wording "cada cliente tem um card no funil" (singular). No v1 requirement calls for a client to re-enter the funnel for a second sale, so a separate `cards`/`opportunities` table is deliberately NOT introduced. This is recorded here as an intentional, visible decision.

Purpose: Every other Phase 2 plan (cadastro, kanban, filters, detail sheet) is pure frontend/Server-Action work over this schema. Getting RLS and the ganho/perdido constraints right here — and proving them with negative-case tests as a restricted Vendedor, not just as Supervisor — is the highest-leverage work in the phase (Pitfalls 1, 2, 3, 6, 10).
Output: One applied migration, the shared `lib/funil/etapas.ts` stage constant (single source of truth for the 7 fixed stages), and two green negative-case test files.
</objective>

<threat_model>
## Trust Boundaries
| Boundary | Description |
|----------|-------------|
| browser (anon/authenticated key) → PostgREST table API | The anon/authenticated key is public; any authenticated user can call the REST API directly, bypassing the UI. RLS + CHECK constraints are the only real boundary. |
| browser → `mover_card_funil` RPC | Funnel writes; the RPC runs as the caller so RLS still applies, but the RPC is bypassable via a raw UPDATE — hence the CHECK constraints. |

## STRIDE Threat Register
| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Information Disclosure | clientes SELECT | high | mitigate | RLS SELECT `responsavel = (select auth.uid()) or is_supervisor()`; proven by the Vendedor-B-cannot-see-A test (not tested only as Supervisor — Pitfall 2). |
| T-02-02 | Elevation of Privilege | clientes UPDATE (responsavel column) | high | mitigate | UPDATE WITH CHECK blocks a Vendedor reassigning responsavel to another user; proven by the reassignment test. |
| T-02-03 | Tampering | status_acompanhamento business rules | high | mitigate | DB CHECK constraints (ganho-only-final, perdido-requires-motivo) enforce the rule against direct API calls, not just the RPC/UI (FUN-05/FUN-06). |
| T-02-04 | Elevation of Privilege | clientes DELETE | medium | mitigate | DELETE policy `using (is_supervisor())` only — a Vendedor deleting is a no-op (CLI-06). |
| T-02-05 | Information Disclosure | tarefas / historico / cliente_produtos joined tables | medium | mitigate | Each joined table has its own EXISTS-on-parent RLS policy (Pitfall 3), not relying on the clientes policy. |
| T-02-06 | Spoofing | role source of truth | low | accept | Role comes from profiles via is_supervisor() (0001), never from client-editable JWT metadata — inherited control, re-used here. |
</threat_model>
