## Documented Defaults — Flagged for Confirmation

Both items below were explicitly called out by `ROADMAP.md`/the phase brief as decisions belonging to this phase, with no upstream answer. No `AskUserQuestion`-equivalent tool was available in this research run, so each is resolved here as a concrete, lowest-risk default — exactly the posture `15-UI-SPEC.md` already established for its own resumo-length decision. **Confirm or override at the plan/execute checkpoint**, not silently.

### D1 — Legacy "concluir tarefa" checkbox in the Funil section (carried over from Phase 15's checkpoint)

**Decision: (a) leave the checkbox exactly as-is this phase.** `Checkbox` + `handleToggleTarefa` (lines ~997–1002, ~411–431) keeps instantly marking a tarefa `concluida = true` with **no resumo prompt** — it does not route through `ConcluirItemDialog`/`concluir_tarefa_prospeccao`, and this phase does not change that.

**Why this default, not (b) require a resumo here too or (c) remove it:**
- (b) would add a resumo-collecting dialog to a component this phase's Notas explicitly scope out ("não piorar" the existing `eslint-disable`, not "expand" this section) — real scope creep beyond ATV-01/ATV-02/DIAR-01.
- (c) removes a working, low-friction completion path from inside the sheet the vendor already has open, forcing a trip to `/agenda` to conclude the same tarefa — directly against `CLAUDE.md`'s core value ("mínimo de fricção").
- (a) costs nothing, breaks nothing, and is safe **specifically because** of how the trigger (`tarefas_before_update_historico`, migration `0015`) already handles it: when `resumo` is null/empty, it writes the generic fallback string `"Tarefa marcada como concluída"` into `historico.descricao` instead of failing. The new Diário (see below) renders whatever `historico` already has — a legacy-checkbox entry shows up with that generic text instead of a real resumo, which is visibly weaker than an Agenda-concluded entry but still structurally valid (still has a date, an author, and *a* descriptive line) and never breaks the diário's rendering contract.

**What this means for the Diário UI:** `DiarioTimeline` (below) must render both shapes (a real vendor resumo, and the generic fallback string) identically — no special-casing, no "missing resumo" warning badge. Treat `descricao` as the entry's body text either way.

### D2 — `frequencia_pedidos` input shape

Migration `0013`'s own comment says explicitly: *"frequencia_pedidos é texto livre de propósito... o vocabulário/validação dele é decisão da Fase 16."*

**Decision (owner-confirmed, overrides the researcher's free-text default): a `Select` backed by a 4th Supervisor-managed CRUD vocabulary, following the exact same pattern already established for categoria/produtos consumidos/tipos de tarefa (Phase 3's "Administração de Listas Editáveis").**

**Technical implication the planner MUST account for (this is a real scope change vs. the ROADMAP's "não exigem migration nova" note):**
- A new lookup table (e.g. `frequencias_pedido`) is needed, mirroring `categorias`/`produtos_consumidos`/`tipos_tarefa`'s existing shape: `id uuid`, `nome text`, RLS readable by all authenticated, write-gated to Supervisor only (`is_supervisor()`), following the exact CRUD-enum pattern already shipped in Phase 3.
- **This DOES require a new migration** — contradicting the phase's original "no new migration" assumption from the roadmap notes. `clientes.frequencia_pedidos` keeps storing the chosen value as plain `text` (matching the existing column type from migration 0013, rather than switching to a foreign key) — simplest path, avoids an ALTER on `clientes`.
- The Select's options come from the new table, same `{value, label}` combobox pattern already used for `categoria` and `produtos_consumidos` in the cadastro form.
- Admin UI: a new CRUD screen/section for Supervisors to manage this vocabulary is in scope for this phase (mirroring the existing categoria/produtos/tipos-tarefa admin UI), since ATV-02 has no value to select from otherwise.
- Zod validation: value must exist in the current vocabulary list (fetched server-side), same validation shape as categoria.

### Data layer changes (`lib/supabase/queries/clientes.ts`, `lib/validations/cliente.ts`, `app/actions/clientes.ts`, `app/actions/funil.ts`)

1. **`ClienteDetalhe` type** gains three new optional-string fields: `nomeFantasia: string | null`, `cnpj: string | null`, `frequenciaPedidos: string | null`. `getClienteById`'s `select()` gains `nome_fantasia, cnpj, frequencia_pedidos`, mapped straight through (no transform) — same pattern every other nullable text column in this function already follows.
2. **`updateClienteSchema`/`UpdateClienteInput`** gain the same three fields as `z.string().optional()`, no `.min()`, no `.regex()` — placed alongside `contato`/`telefone`/`email` in the schema, not in a separate schema (this phase does **not** introduce a dedicated "atualizar cliente ativo" Server Action; it extends the existing `updateCliente` write path, since these are ordinary cliente columns with no special atomicity/RLS requirement the way `frequenciaVisita`'s dedicated `atualizarFrequenciaVisita` action has). `toFormValues` gains the matching three `?? ""` defaults.
3. **`createClienteSchema`/`ClienteQuickCreateForm.tsx` are untouched** — this is the literal mechanism behind success criterion 1's "cadastro rápido... continua sem pedir nenhum dos dois."
4. **New `DiarioEntry` type + `getDiario(clienteId)` query function**, co-located in `lib/supabase/queries/clientes.ts` next to `getHistorico`/`HistoricoEntry`:
   ```
   export type DiarioEntry = {
     id: string
     tipo: "tarefa_concluida" | "visita_concluida"
     descricao: string
     criadoEm: string
     autorNome: string | null
   }

   export async function getDiario(clienteId: string): Promise<DiarioEntry[]> {
     const supabase = await createClient()
     const { data, error } = await supabase
       .from("historico")
       .select("id, tipo, descricao, criado_em, profiles(nome, sobrenome)")
       .eq("cliente_id", clienteId)
       .in("tipo", ["tarefa_concluida", "visita_concluida"])
       .order("criado_em", { ascending: false })
     if (error || !data) return []
     return data.map((row) => ({
       id: row.id,
       tipo: row.tipo as DiarioEntry["tipo"],
       descricao: row.descricao,
       criadoEm: row.criado_em,
       autorNome: row.profiles ? `${row.profiles.nome} ${row.profiles.sobrenome}` : null,
     }))
   }
   ```
   Filtering by `tipo` happens **in the query**, not client-side over the already-loaded `historico` array — the Diário is a distinct read from the existing full-audit-trail `getHistorico`, not a client-side filter of it (mirrors this project's existing "narrow `select()`, filter in SQL" convention).
5. **New `getDiarioAction(clienteId)` Server Action**, co-located in `app/actions/funil.ts` next to `getHistoricoAction` (identical thin-wrapper shape: `{ data: DiarioEntry[] } | { error }`).
6. **RLS: zero new policies needed.** `historico`'s existing parent-gated SELECT policy (migration `0002`, unchanged) already scopes every read — a Vendedor's `getDiario` call returns only their own clientes' entries, a Supervisor's returns any cliente's, satisfying success criterion 4 for free, exactly the same way `getHistorico`/`AGD-04` already do.

### `components/clientes/DiarioTimeline.tsx` (new — structural sibling of `HistoricoTimeline.tsx`)

```
export function DiarioTimeline({ entries }: { entries: DiarioEntry[] }) {
  if (entries.length === 0) {
    return <p className="text-sm text-muted-foreground">Nenhuma visita ou tarefa concluída ainda.</p>
  }
  return (
    <ol className="flex flex-col gap-1.5">
      {entries.map((entry) => (
        <li key={entry.id} className="flex flex-col gap-1.5 rounded-lg border p-3">
          <div className="flex items-center justify-between gap-2">
            {entry.tipo === "tarefa_concluida" ? (
              <Badge variant="outline" className="shrink-0"><ClipboardCheck />Prospecção</Badge>
            ) : (
              <Badge variant="secondary" className="shrink-0"><Repeat />Visita</Badge>
            )}
            <span className="text-xs text-muted-foreground">
              {format(parseISO(entry.criadoEm), "dd/MM/yyyy HH:mm")}
            </span>
          </div>
          <p className="text-sm">{entry.descricao}</p>
          <p className="text-xs text-muted-foreground">
            {entry.autorNome ?? "Autor não identificado"}
          </p>
        </li>
      ))}
    </ol>
  )
}
```
Read-only, no interaction, no write controls anywhere — same explicit posture `HistoricoTimeline.tsx`'s own header comment already states ("no write controls... T-02-25: only SECURITY DEFINER triggers ever populate historico"). The bordered-card-per-entry treatment (`rounded-lg border p-3`) is a deliberate visual upgrade over `HistoricoTimeline`'s flatter single-line-per-entry style, because a Diário entry carries structured metadata (origem badge + autor) `HistoricoTimeline` doesn't render at all — reusing the exact `rounded-lg border p-3` class this same file already uses for the `addingTarefa` block, not a new container style.
