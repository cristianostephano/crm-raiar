## Copywriting Contract

### New dialog — `GanhoFrequenciaDialog.tsx` (new file, sibling to `PerdaMotivoDialog.tsx`)

Mirrors `PerdaMotivoDialog.tsx`'s structure exactly (required-select-before-confirm pattern), with two deliberate differences: **(a)** the 4 frequência options are a static enum, not a DB-loaded lookup table, so there is no `Carregando...`/load-error state — the `Select` is populated immediately; **(b)** the confirm button uses the **default/primary** variant, never `destructive`.

| Element | Copy |
|---------|------|
| Dialog title | `Marcar {razaoSocial} como ganho?` |
| Field label | `Frequência de visita` |
| Select placeholder | `Selecione a frequência` |
| Select options (in this order) | `Semanal` / `Quinzenal` / `Mensal` / `Nenhuma` |
| Helper text (shown while nothing is selected, same slot as `PerdaMotivoDialog`'s `REQUIRED_MOTIVO_MESSAGE` idle state) | `Escolha a frequência de visita para este cliente.` |
| Validation error (submit attempted with nothing selected — defense-in-depth only, button is already disabled) | `Selecione a frequência de visita antes de confirmar.` |
| Submit error (RPC/save failure) | `Não foi possível salvar as alterações. Tente novamente.` (reuse `GENERIC_ERROR`, do not invent new copy) |
| Cancel button | `Cancelar` |
| Confirm button (idle / submitting) | `Confirmar ganho` / `Salvando...` |
| Confirm button variant | `default` (primary) — **not** `destructive` |
| Confirm button disabled condition | disabled whenever no option is selected, or while submitting — mirrors `PerdaMotivoDialog`'s `disabled={isSubmitting || isLoading || !selectedMotivoId}` (drop `isLoading`, there's nothing to load) |

### Standing frequência control — `ClienteDetailSheet.tsx`, inside the existing "Funil" section

Renders **only when `cliente.statusAcompanhamento === "ganho"`**, directly below the existing Status `Select` (`cliente-status-select`), same `flex flex-col gap-1.5` field block pattern. This is the VIS-02 "editable or cancelable at any time" control — it must render even for clients already `ganho` before this phase shipped, since their `frequencia_visita` is `NULL` (VIS-04) and this is the only place to set one for the first time.

| Element | Copy |
|---------|------|
| Field label | `Frequência de visita` |
| Select placeholder (shown when `frequencia_visita` is `NULL`) | `Selecione a frequência` |
| Select options | `Semanal` / `Quinzenal` / `Mensal` / `Nenhuma` |
| Helper text — legacy/undefined state (`frequencia_visita is NULL`, VIS-04) | `Frequência ainda não definida.` |
| Save error | `Não foi possível salvar as alterações. Tente novamente.` (reuse `GENERIC_ERROR`) |
| Destructive confirmation | **None.** Changing to or from `Nenhuma` is an ordinary preference edit, not a destructive action — per VIS-02's explicit "editável ou cancelável a qualquer momento" with minimum friction. Do not add a confirm dialog for this control |

Interaction: immediate-save on `onValueChange` (no separate "Salvar" step), mirroring the existing Status `Select`'s own immediate-save behavior in the same section — not bundled into the Sheet's `react-hook-form`-driven "Salvar alterações" submit at the bottom, which only covers the "Dados do cliente" section.

### No other CTA, empty state, or destructive action is introduced by this phase

The first `visitas` row seeded on `ganho` (VIS-01 point 2) and the per-client visit diary (VIS-02/DIAR-01) are **not** rendered anywhere in Phase 13's UI — those surfaces belong to Phase 14 (Agenda) and Phase 16 (Diário). Phase 13's entire UI surface is the two elements above.

## Interaction Contract (supplements the Copywriting Contract — the "where does this wire up" detail the checker/executor needs)

1. **Entry point is `ClienteDetailSheet.tsx`'s existing `handleStatusSelect`**, not `KanbanBoard.tsx`'s drag handler. Marking "ganho" already only happens through the Status `Select` inside the Sheet (the `ganho` `SelectItem` is `disabled` unless `cliente.etapa === ETAPA_FINAL` — this gating is unchanged). Add a `"ganho"` branch there, structurally identical to the existing `"perdido"` branch:
   ```
   if (novoStatus === "perdido") { setPerdaDialogOpen(true); return }
   if (novoStatus === "ganho") { setGanhoDialogOpen(true); return }
   void handleStatusChange(novoStatus)
   ```
2. `handleStatusChange` gains an optional `frequenciaVisita` parameter (sibling to its existing `motivoPerdaId` parameter), threaded through to `marcarStatus`/`mover_card_funil` exactly as `motivoPerdaId` already is.
3. `GanhoFrequenciaDialog`'s `onConfirm(frequencia)` prop signature mirrors `PerdaMotivoDialog`'s `onConfirm(motivoId)` exactly: `(frequencia: string) => Promise<{ error?: { message: string } } | undefined>`, wired to `handleStatusChange("ganho", undefined, frequencia)`.
4. The standing frequência `Select` in the Funil section calls a **new**, separate handler (e.g. `handleFrequenciaChange`) — it must never re-invoke `mover_card_funil` (that RPC's purpose is specifically the funnel-stage/status transition, per `ARCHITECTURE.md` Pattern 4) — it's an ordinary `clientes` field update, same trust boundary as `observacao`.
