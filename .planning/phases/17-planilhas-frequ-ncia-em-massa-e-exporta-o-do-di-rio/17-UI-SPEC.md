# Phase 17 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase ships **two independent, reused-pattern flows**, both explicitly required by `ROADMAP.md` to reuse existing screens rather than invent new ones:

- **IMP-01 (Frequência em massa):** a new Supervisor-only screen that walks the *exact same 4-step shape* as the v1.1 client-import wizard (`enviar → mapear → revisar → confirmar`), but with a materially different backend contract — it **updates** `clientes.frequencia_visita` on existing "ganho" clients, it never creates a client, and its confirm step calls a brand-new RPC.
- **IMP-02 (Exportar diário):** a new "Exportar diário" download button, styled and wired identically to the already-shipped "Exportar meus/todos os clientes" button (Phase 5), but reading from `historico` (tipo `tarefa_concluida`/`visita_concluida`) instead of `clientes`.

There is no `CONTEXT.md` (discuss-phase was skipped) and no phase-level `RESEARCH.md` — this contract is built from `ROADMAP.md`'s "Notas para o planejamento", `REQUIREMENTS.md` (IMP-01, IMP-02), the milestone-level research docs (`ARCHITECTURE.md`, `FEATURES.md`, `PITFALLS.md`), the v1.1 archive (`milestones/v1.1-ROADMAP.md`, Phases 5-7), and direct inspection of the actual shipped code: `ImportWizard.tsx`, `ImportPreviewTable.tsx`, `ImportSummary.tsx`, `ColumnMappingTable.tsx`, `FileDropzone.tsx`, `lib/importacao/*`, `lib/clientes/exportacao.ts`, `app/api/clientes/exportar/route.ts`, `KanbanBoard.tsx`'s Exportar button, `AgendaList.tsx`, `AppSidebar.tsx`, `lib/funil/frequencia.ts`, and migrations `0002`/`0013`/`0015`. No interactive question tool was available in this run; every open product question below is resolved as an explicit, documented default (same posture `16-UI-SPEC.md` already established for its own two open questions) — **flag for the project owner to override at the plan/execute checkpoint if they disagree**, rather than blocking this contract.

All visual tokens below are the project's **existing, already-shipped** design system (shadcn `base-nova` + Base UI + Tailwind v4 `@theme`); nothing new is introduced.

## Documented Defaults — Flagged for Confirmation

Four placement/reuse decisions had no explicit answer upstream. Each is resolved here as the lowest-risk, most-consistent-with-precedent default.

### D1 — IMP-01 gets its own route, not a second tab on `/clientes/importar`

**Decision: new route `/clientes/importar-frequencias`, own page, own nav entry — not tabs bolted onto the existing `ImportarClientesPage`.**

Why: the two flows share a *screen pattern* (enviar → mapear → revisar → confirmar), not a *data model* — different system fields (2 vs 14), different row-status vocabulary (`ok`/`erro` only, no `duplicado`), different confirm RPC, different "what gets written" semantics (UPDATE vs INSERT). Cramming both into one wizard component would need step-1 branching logic no existing component has, for a savings of one nav click. A second route costs nothing and keeps `ImportWizard.tsx` (the client-creation flow, already in production) completely untouched.

### D2 — "Exportar diário" lives on the Agenda page, not the Clientes page or a new report screen

**Decision: the export button renders inside `AgendaList.tsx`'s header, mirroring `KanbanBoard.tsx`'s existing "Exportar" button exactly.**

Why: the Agenda screen is where vendedores work `tarefas`/`visitas` day to day (the same two sources the diário reads from, just the completed slice instead of the pending slice) — it's the closest thematic home even though `AgendaList` itself only ever renders *pending* items. The Clientes/Kanban screen already owns a differently-scoped export (client roster); adding a second, differently-sourced download button there would blur what each button does. No new route/page is created for this — it's one button inside an existing screen, exactly like Phase 5 added one button inside the existing Kanban screen.

### D3 — The diário export ignores the Agenda's active "Vendedor" filter

**Decision: clicking "Exportar diário" always exports the caller's full RLS-visible diário (own clientes for a Vendedor, the whole team for a Supervisor), regardless of whatever vendedor the Supervisor currently has selected in the Agenda's filter Select.**

Why: success criterion 5 only asks for role-based visibility ("própria x todos"), not filter-scoped export (unlike Phase 5's `EXP-03`, which was an explicit, named requirement). Threading the filter through would need the export button to know about a state variable it currently has no reason to read, for a feature nobody asked for. Simpler contract, zero ambiguity: the button always means "everything I'm allowed to see."

### D4 — `ColumnMappingTable.tsx` gets one new optional prop, not a duplicate component

**Decision: add `fields?: SystemFieldDefinition[] = SYSTEM_FIELDS` to `ColumnMappingTable`'s props, threaded straight into its `SelectItem` map — the one existing file this phase modifies.**

Why: `lib/importacao/mapping.ts`'s own `suggestMapping`/`requiredFieldsFaltando` **already** accept an optional `fields` parameter defaulting to `SYSTEM_FIELDS` — the pure-logic layer was already built to support a second vocabulary; only the presentational component never got the matching prop. Adding it is a one-line, backward-compatible change (existing call site in `ImportWizard.tsx` needs no edit) that lets `FrequenciaImportWizard` reuse the exact same table instead of forking it.
