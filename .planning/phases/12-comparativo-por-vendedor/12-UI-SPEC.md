# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase adds exactly ONE new dashboard section — `ComparativoVendedorTable.tsx`, a Supervisor-only table with one row per ACTIVE vendedor (`role='vendedor' and profiles.ativo=true`), comparing taxa de conversão, negócios iniciados, negócios ganhos, and ciclo médio em dias (VEND-01). No new screen, no new type scale, no new color, no new npm dependency, no new shadcn component. Every token below is reused exactly from Phase 8-11's approved UI-SPECs.

## Component-Specific Implementation Notes

*(Extends the template — this phase's contract lives mostly here, mirroring Phase 11's precedent for a table-shaped dashboard component.)*

### 1. `ComparativoVendedorTable.tsx` — the VEND-01 table

**Card wrapper:** identical structure to `FunilDetalhadoTable.tsx` — `Card` > `CardHeader` (`CardTitle` "Comparativo por vendedor" at `text-[20px] font-semibold`, `CardDescription` "Histórico completo — não é afetado pelo filtro de período") > `CardContent` holding the `Table`.

**Row order:** alphabetical by `responsavelNome` (matches the RPC's own `order by v.nome` per RESEARCH.md's Code Examples, and `lib/equipe/membros.ts`'s `substitutosDisponiveis` sort precedent). Rows are never re-sorted by any column value or click-to-sort affordance — this is a static comparison list, not an interactive sortable table (no sort arrows in column headers, matching `FunilDetalhadoTable`'s own non-sortable posture).

**Columns (5, in this exact order):**
1. **Vendedor** — `responsavelNome` text, `font-medium` (matches `FunilDetalhadoTable`'s "Etapa" column / `ImportPreviewTable`'s "Razão social" column precedent — the row's identifying column gets the emphasis weight, nothing else does).
2. **Taxa de conversão** — `taxaConversao(ganho, perdido)` (reused from `lib/dashboard/periodo.ts`, D-03) formatted via the existing `percentFormatter`, or "—" when null.
3. **Negócios iniciados** — plain integer via `integerFormatter`, never "—" (D-01: all-time count, always defined, 0 is a real answer).
4. **Negócios ganhos** — plain integer via `integerFormatter`, never "—" (same reasoning as above).
5. **Ciclo médio (dias)** — `"{N} dias"` (1 decimal) or "—" when null (zero ganho closings for that vendedor). Column header carries a `CircleHelp` tooltip (`size-3.5 text-muted-foreground`, wrapped in the existing `Tooltip`/`TooltipTrigger`/`TooltipContent` primitive) with the D-04 disambiguation copy from the Copywriting Contract above — identical visual pattern to `FunilDetalhadoTable`'s "Quantidade" tooltip. Do not add a second line of visible helper text under the tooltip trigger — the tooltip is the only disambiguation surface, keeping the header row height identical to every other column.

**No bottleneck/warning row highlight:** unlike `FunilDetalhadoTable`'s D-03 amber "Gargalo" treatment, every row here renders with default `TableRow` styling — no conditional border, no badge. This phase's success criteria (ROADMAP.md Phase 12) define no low-performance flag; do not invent one.

**Loading state:** `Skeleton className="h-[320px] w-full"` inside `CardContent` — matches `FunilDetalhadoTable`'s actual established table-card skeleton height exactly (verified against `FunilDetalhadoTable.tsx`; `280px` is a different, chart-shaped precedent — `ClientesPorEtapaChart`/`DesempenhoVendedorChart` — not applicable to a table-shaped component).

**Error state:** identical structure/copy to `FunilDetalhadoTable`'s error branch — centered `flex h-[320px] w-full flex-col items-center justify-center gap-3 text-center` with the exact retry copy/button from the Copywriting Contract above, its own independent `reloadKey`/`FetchState` (never blocks the rest of `DashboardClient` from rendering, matching every other dashboard card's isolation).

**Empty state:** when the active-vendedor row list itself is empty (zero rows returned by the RPC — edge case, e.g. every vendedor deactivated), render the same centered empty message pattern as `FunilDetalhadoTable` ("Nenhum vendedor ativo no momento.") INSTEAD OF an empty table — do not render a table with zero rows and no explanation. This is distinct from the "zero-clientes row" case above (an active vendedor who simply has no clientes yet still gets a full dashed row, per RESEARCH.md Open Question 2 — only the "there are no active vendedores at all" case triggers this empty state).

**No client-side re-filtering by `ativo`:** the RPC already excludes deactivated vendedores at the SQL layer (`vendedores_ativos` CTE, per RESEARCH.md Pattern 2) — this component must never add its own `.filter(v => v.ativo)` or similar client-side re-check; every row the RPC returns is rendered as-is, in the order received.

**No role-based visual variant:** this component assumes it is only ever mounted for a Supervisor — `DashboardClient` owns the `isSupervisor` gate (see Placement below) — so it performs no role check of its own and never branches on `isSupervisor` for appearance or layout, matching `DesempenhoVendedorChart`'s established precedent exactly.

### 2. Placement in `DashboardClient.tsx`

Insert `ComparativoVendedorTable` (gated by `{isSupervisor ? <ComparativoVendedorTable /> : null}`) immediately after `TempoAteFechamentoCards` and before `GanhosPerdidosCards`, extending the existing whole-history/un-period-filtered block that already contains `ClientesPorEtapaChart` → `FunilDetalhadoTable` → `TempoAteFechamentoCards`. This component takes zero period parameters (per D-02, RESEARCH.md Pattern 4), making it un-period-filtered exactly like its two block-mates — it does NOT sit next to `DesempenhoVendedorChart` (which remains period-filtered and Supervisor-only, unchanged by this phase, still driven by `periodo.inicio`/`periodo.fim`). This confirms and extends Phase 11's own placement convention (un-period-filtered sections stay adjacent, grouped before the `PeriodoFilter`-driven sections) rather than introducing a new grouping rule — interleaving period-filtered and whole-history sections is NOT fine; the two groups stay visually separated as an ordered stack, matching the existing precedent exactly.

```tsx
// components/dashboard/DashboardClient.tsx — extends the existing block
<ClientesPorEtapaChart />
<FunilDetalhadoTable />
<TempoAteFechamentoCards />
{isSupervisor ? <ComparativoVendedorTable /> : null}

<GanhosPerdidosCards inicio={periodo.inicio} fim={periodo.fim} />
{isSupervisor ? (
  <DesempenhoVendedorChart inicio={periodo.inicio} fim={periodo.fim} />
) : null}
{/* ProspeccaoChart pair, unchanged */}
```
